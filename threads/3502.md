## Description

A tracking table for the shader work, not a fix. Every program the title refused in the world on our build is one row, with the translator's own error text, the program's job in plain words, and the PR(s) that make that program translate on each of the two host wave sizes. The two columns differ because most of these programs are refused *only* on hosts without 64-lane waves.

Rows are grouped by failure class, then by subsystem. `—` in the AMD column means **no PR is needed**: the refusal cannot fire on a 64-lane host (the error text says so). The one such row that also appears in #293's AMD ranking, `2561af95`, is refused there for a different reason, which is why its AMD cell is not empty.

## C. Pipelines the host refuses (the shader translates, `CreatePipelineState` fails)

A draw is just as missing when the driver refuses the pipeline (`dropped ... refused [compute <hash>]`) as when the translator refuses the shader, but the cause and the fix lie in the driver or layer, so these are kept apart from A and B. Rows are per host; anyone seeing `refused [...]` on another GPU can add rows: hash, host (GPU, driver, layer), drops per frame, what `VICTORY_D3D12_DEBUG=1` reports, PR or workaround.

**No entries so far.**
- RTX 5090, Linux, Wine + vkd3d-proton: our runs have no `refused [` drop lines.
- RX 9070 XT, AMD fork `4eb6cfd` (@rpmaster2): the 34 pipelines first listed here turned out to be skipped by that fork's list of pipelines that crashed the AMD compiler in earlier runs (`warm-bad.txt`), so no `CreatePipelineState` was attempted. That fork labels such skips `refused [...]`; on `main` a skip is labelled `skipped shader` (`crates/victory-gpu/src/pipeline.rs`) and `main` has no such list, so on `main` the label means a real host refusal.

## What the two columns say

* **43 of the 50 are wave-size-only.** 33 need a group larger than 64 threads (W), 9 an implicit-derivative sample in the console flow (D), one a whole-wave section (S). On a 32-lane host they are the entire content of the #2176 → #2711 → #2925 stack, which translates 42 of the 43 — all but `5b2ce592`, which needs #2999 — with no changed DXIL bytes on anything the base already translated. On a 64-lane host none of them is refused at all; whether they then translate depends on other reasons — `2561af95` hits one there.
* **The nine D rows are a translate fix, not a validation fix.** An implicit sample in a compute module still needs validator 1.8 (#1065) to pass `--validate`, and the console's lane-quad order (#1237, #2999) to pick the right mip. That is true on both hosts, so the `—` in the AMD column means "not refused", not "correct".
* **The stack leaves 8 of the 50 refused**, and two of them carry the largest remaining drop counts on our host (`82a2ad6d` 7.3/5.0, `90a0692a` 2.4/2.4). Three clear offline with one PR each (#2363, #1014, #2999); the other five have candidate PRs per #1247 (offline, on a 64-lane AMD host) and are waiting on a 32-lane census (two `v_cvt_f32_f64`, two `a lane mask read as data`, one barycentric interpolation).
* **The two hosts refuse different programs for the same pass.** `2561af95` (particle light atlas, sprite) is the top of #293's AMD ranking at 37.4/frame refused as "a lane-mask join of an untracked mask"; on our host it is the top of the D class at 18.5/frame peak refused as an implicit-derivative sample. A single fix for either host does nothing for the other.
* **#439 is a prerequisite, not the fix, for groups above 64 threads.** It gives the console flow for one console wave; on plain `main` the #2176/#2711/#2925 stack still reaches 41/42, so merge order is a build-policy question (#439 needs #2118 alongside), not a coverage one.
* **The BVH builder is the one place where translating more is worse.** `14394a32` translating while a sibling stayed refused crashed the title (#439 comment, #2118); the all-or-none gate has to land with the stack, not after it.

## Open gaps

1. **No 64-lane host has run this stack.** Every `—` in the AMD column is the reason text plus #293's older AMD run, not a measurement of these 50 programs on an AMD card. That is the largest single inference in this table.
2. **No DXIL validation anywhere in our chain** (`dxil.dll` is absent from the Wine prefix and the xwin SDK), so "translates" means "emits", not "a pipeline the host created". #439's own thread reports the same gap.
3. **Five rows have candidate PRs but no 32-lane measurement.** #1247 reports, offline and on a 64-lane AMD host: #3016 with #385 for the last 4 `a lane mask read as data` programs (+4, 0 lost), #2978 + #385 + #2999 (or #1065) for all 5 `v_cvt_f32_f64` programs, and #3335 + #1738's change for the barycentric one (+1). None of those three combinations has been run against a 32-lane host; that is the pending census.
4. **#2126 (2-D group thread-id tiling) is only half measured.** chippy01 probed 32x2 exactly on a 3070 Ti and named `CS_AmbientMapSky*` as the title's affected rows; our 21 cascade rows and 4 light-atlas rows are tiled too, but the per-program `[numthreads]` is not in the info-level logs.
