## Description

## Summary
Fixes #2256 (indirect clamp and direct Dispatch cutting compute dispatches with more than 65,535 groups in x).

1. **Shader side (`victory-shader`):**
   - Adds `DISPATCH_SLOT` user-data constants (ow, ^Gsked_x) and a compute prologue (cs_spread_prologue) emitted after self.inputs() (so entry-block inputs dominate the body block).
   - When ow != 0, remaps GroupId(0) to x + z * row, GroupId(2) to , and returns early before the shader body if eff_x >= asked_x (covering side-effect-only shaders that do not read TGID).
2. **GPU side (`victory-gpu`):**
   - **Direct `Dispatch`:** spreads x > 65,535 && z == 1 into ceil(x / rows) x y x rows (ows = ceil(x / 65,535)) and passes [row, asked_x] via DISPATCH_SLOT user data.
   - **Indirect `ExecuteIndirect(DISPATCH)`:** `indirect::bound_spread` writes 20-byte [row, asked_x, gx, gy, gz] records into a list-kept UAV buffer (zeroing g_out when over budget), and `draw::execute_indirect` runs them through a cached root-constant + dispatch command signature (host_spread_signature).

We were about to add a limit check for direct dispatches and found this PR already covers the main case (x > 65,535 with z == 1). Two notes, from reading the code only; I didn't run anything.

1. **The host spreads even where the shader has no remap.** In `draw.rs`, `spread_groups` runs for every direct dispatch, whatever the program. But the translator emits `cs_spread_prologue` only when the entry block isn't a loop header (`!self.counters.contains_key(&order[0])` in `lower.rs`). For a compute program whose first block is a loop header, x > 65,535 is dispatched as `(row, y, rows)` with no remap:
   - groups `row..x` never run;

@upipibi Great comparative analysis with `xcl#1428` and `shadPS4#5479`. A few key architectural differences that make the Z-spread approach particularly clean here:

1. **Preserving 2D dispatches (`y > 1`):**
   Folding X into Y only works when `y == 1`. In title workloads (such as wide G-buffer/tiled compute passes), dispatches are frequently 2D `(width_tiles, height_tiles, 1)` where `width_tiles > 65,535` and `height_tiles > 1`. Spreading across Z keeps Y completely independent and unmodified (`gx = row`, `gy = y`, `gz = rows`), correctly covering wide 2D grids without clamping.

2. **Unified Pipeline Cache Key (No Direct vs Indirect Splitting):**
   Unlike shadPS4's split cache keys, in Victory both direct and indirect dispatches use the **exact same** `HostPipeline` and root signature:
   - In direct dispatch, `State::dispatch` injects `[row, asked_x]` into root constants via `DISPATCH_SLOT`.
   - In indirect dispatch, `bound_spread` writes `[row, asked_x, row, y, rows]` into the indirect arguments buffer, and `host_spread_signature` extracts `row` and `asked_x` into the exact same root constant indices before dispatching `gx, gy, gz`.
   Because the shader's `cs_spread_prologue` reads `row` and `asked_x` from root constants regardless of how the command list was recorded, a single compiled compute PSO seamlessly services both direct and indirect calls without cache duplication or recompilation overhead.

A performance data point for the indirect path, from a fork that carries this change (RTX 5080, driver 621.40, Windows 11 build 26300, diagnostics build).

With every indirect dispatch of a program that declares `DISPATCH_SLOT` going through the spread command signature (the `CONSTANT` argument writing the two words, then the dispatch), about 960 indirect dispatches a frame took that signature in the first gameplay area, while about one record a frame asked for more than 65,535 groups in x. On this card that signature is the expensive part. In one run, with only that path switched every 20 seconds (same build, same scene), the frame was 67.4 ms with the spread signature for every record against 53.0 ms with the lean form below (14.8 against 18.9 fps): about 15 microseconds of the card's time per `ExecuteIndirect` with root constants.

The lean form is fxceless/victory-fork#1352 (by grosterr). The clamp writes each record that fits within 65,535 groups for the plain dispatch signature (the program's two spread words are 0 from its bind, so it runs unspread), and only a record past 65,535 is written for the spread signature, which runs under a predicate the clamp sets only for such a record (`SetPredication` on the clamp's output). Every record still runs whole; nothing is clamped to 65,535 either way. On the card that is two `ExecuteIndirect` calls per dispatch, the second predicated off nearly always, and no root constants on the common path.

So on NVIDIA it may be worth taking that form here, or at least keeping the constants off the path of records that fit.
