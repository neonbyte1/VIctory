# Marvisak/VIctory#3120: GPU: with VICTORY_GPU_OVERLAP=1, the title's submissions return before the host GPU has run them

- PR by @0xkn0wh3r3, opened 2026-11-26T08:51:39Z, state **open**
- <https://github.com/Marvisak/VIctory/pull/3120>
- Archived copy; the original thread is authoritative while it exists.

## Description

With `VICTORY_GPU_OVERLAP=1`, ExecuteCommandLists no longer waits for the host GPU. The title's lists go to the host queue with a Signal of the host fence, and the call returns. The submission completes later: what shaders wrote goes back to title memory, then the lists' work after them and their bottom-of-pipe writes, then the title fences its queue signalled behind it. A completion thread completes each submission once the GPU has run it, so a title's fence moves, and its waits end, without any call from the title, as on the console. A title that keeps frames in flight then gets them: it records the next frame while the GPU runs the last.

**Off by default.** Without the switch, every submission is waited for as on `main`, and the swap chain keeps two buffers. Whether to turn it on is the maintainer's call, after a run of the actual title (see Evidence).

## What still waits, with overlap on

A submission completes the ones it needs before it is prepared. The wait is for the host fence, with the submission lock released.

- **Completion writes title memory or takes write marks:** declared shader writes (copy-backs), title memory through page tables, missed-read checks, work after the lists, bottom-of-pipe writes, or marks together with heap indexing. Such a submission completes before the next is prepared, because the next one's refreshes and copies read title memory and its shaders mark in the same bitmaps.
- **Title copies and work that write title memory on the CPU** (for the GPU's timeline) wait for everything before them.
- **The upload list** waits for its own last run, and a host list waits for its own previous run.
- **Read marks** are cleared only when no submission whose shaders mark reads is in flight, because the GPU's ORs into the bitmap are not atomic with the CPU's clears. The once-a-frame eviction pass clears every read mark, so the title's first submission of a frame first completes those submissions. A completion takes forgotten slots' clears only when none is left marking; otherwise a later one does. Reading marks while a submission may still set more is harmless: what isn't seen yet is seen by a later call.

So only submissions without such writes overlap. GTA VI's lists have bottom-of-pipe writes, so it would overlap much less than the measurements below. Snapshots and bitmaps per submission would lift that.

## Other changes

- A queue's Signal behind work in flight is owed by that queue's last submission and set when it completes, in order, under the submission lock.
- A blocking fence wait (SetEventOnCompletion with no event) now blocks until the value is reached instead of returning E_NOTIMPL.
- Present copies into the swap chain from a ring of three lists. With overlap on, it does not wait for the frame, keeps its planes alive on its list until that has run (not the back buffer, which the swap chain keeps), and the swap chain has three buffers. A resize, multi-plane composition and diagnostics read-backs still wait for what they need.
- Held queue work is pumped after submissions complete on any thread.
- With overlap on, a PresentX on a queue that still holds work (a wait for another queue's fence or memory value) is queued behind that work, and the frame is shown once that work has gone to the host GPU. Without overlap it runs at once, as on `main`. The frame line counts queued presents.
- Host textures given up by eviction, and resources retired while work is in flight, are released once the next submission has completed.
- A title list reset while its host list is still in flight keeps what it owned until that host list is reset, rather than as work run after the list.
- Per-list timing (`VICTORY_GPU_TIMING`) and capture-listed frames always wait.

What the runs show:

- **The result depends on the host.** The world's submissions write title memory when they complete (copy-backs, bottom-of-pipe writes), so each completes before the next is prepared, and preparing, the GPU and copying back mostly stay in series: Kajanos's and imjustprism's hosts gained nothing. neonbyte1's host gained about 16% at 20af9470, all of it in less waiting for the GPU. Three real concurrency/lifetime issues turned up during code review that should be fixed before merging:

### 1. Async `present_with_compositor` does not keep source `planes` alive on `copy` (`crates/victory-gpu/src/host.rs:3785-3985`)
Previously `present_with_compositor` called synchronous `self.execute(&[&p.copy])`, so `&ID3D12Resource` entries in `planes` stayed alive until the copy/composite finished on the GPU. Now that it submits asynchronously via `self.submit(0, vec![copy.clone()])` and returns while `copy` is still in flight, `copy` never calls `copy.keep(tex)` on any plane in `planes` (nor on `&back` if anything could drop it). If the title releases or evicts a presented texture before `copy` finishes on the host GPU, the GPU reads a destroyed resource. Adding `for &(tex, _) in planes { copy.keep(tex); }` before `copy.close()` closes this UAF window.

### 2. Non-atomic `&mut [u32]` + `std::mem::take` on read-mark bitmaps while the GPU writes them (`crates/victory-gpu/src/shadow.rs:828-885`)
With overlapping submissions, the host GPU can execute `InterlockedOr` on the mapped read-mark bitmap concurrently with `take_reads()` / `reads_since()`. Forming `&mut [u32]` via `std::slice::from_raw_parts_mut` and running `std::mem::take(word)` (a separate non-atomic load and zero store) is both a Rust data race (UB) and loses any GPU read mark set between the load and the clear. Using `&[std::sync::atomic::AtomicU32]` with `word.swap(0, Ordering::AcqRel)` eliminates both the UB and the lost-bit window on coherent memory.

### 3. Completions drained by `complete_while` do not pump held queue work (`crates/victory-gpu/src/host.rs:544-550, 598-612`)
`complete_in_background` calls `crate::queue::pump_held_if_free(Why::Completed)` after draining `submitted.flight`, whereas `complete_while` (used by `complete_all`, `complete_held`, `Host::execute`, and `Host::submit`) does not. If a non-`queue::pump` caller (such as `Present` calling `complete_held` / `complete_all`, or `Host::execute`) drains a submission that wrote a bottom-of-pipe memory value or signalled a title fence that another queue's held work is waiting on, `complete_in_background` wakes to an empty `flight` (`completed == false`) and skips pumping — leaving held work stalled until the next title call or background timer tick. Calling `pump_held_if_free(Why::Completed)` after `complete_all`/`complete_held`/`execute` finishes any in-flight record (once `submitted` is dropped) closes this gap.

However, two regressions/bugs were caught in `a75fc056..92137df3`:

### 1. `copy.keep(&back)` breaks `ResizeBuffers` on every swap-chain resize (reproduced on RTX 5090 and WARP, even with `VICTORY_GPU_OVERLAP=0`)
At `crates/victory-gpu/src/host.rs:4040`, `copy.keep(&back)` stores a COM reference to the swap chain's back buffer in `copy.deferred().keep`, which is only cleared when `copy.reset()` runs. When a resize is needed (`host.rs:3814-3828`), `self.complete_all()` waits for in-flight work but never clears `keep` on `p.copies`, so the ring's present lists still hold references to the old back buffers when `p.swap_chain.ResizeBuffers(...)` is called, causing it to fail with `DXGI_ERROR_INVALID_CALL`.

Locally verified on Windows 11 (`cargo test -p victory-gpu --features diagnostics --lib host::present_plane_tests::compositor_failure_presents_primary_in_the_same_frame`):
- RTX 5090 (`overlap=1`, `debug=0` and `debug=1`): **FAILED** at `host.rs:4708` (`compositor initialization can be retried after failure`)
- WARP (`overlap=1` and `overlap=0`, `debug=0` and `debug=1`): **FAILED** at `host.rs:4708`

Note this also breaks the default non-overlap path (`VICTORY_GPU_OVERLAP=0`) because `copy.keep(&back)` runs unconditionally. Clearing `keep` on every list in `p.copies` right after `self.complete_all()` (before `ResizeBuffers`) — or releasing `keep` on completion — fixes it.

### 2. Lost-wakeup race on `COMPLETED` in `Host::finish` (`host.rs:1171-1185, 1790, 1933-1935`)
`COMPLETED.store(true, Ordering::Relaxed)` runs on the very first line of `Host::finish` (`host.rs:1790`), *before* `self.wait_for(record.value)`, copy-backs, bottom-of-pipe writes, and `set_title_fence(fence, value)` (`host.rs:1934`).

If Thread A drops the `submitted` lock after S1 (just before calling `pump_after_completions()`) while Thread B enters `finish()` for S2, sets `COMPLETED = true`, and blocks in `wait_for(S2)` (potentially milliseconds):
1. Thread A runs `COMPLETED.swap(false, Relaxed)` -> observes `true`, resets it to `false`, and calls `pump_held_if_free` *before* S2's writes or fence signals happen.
2. Thread B finishes `wait_for(S2)`, performs S2's writes and `set_title_fence`, drops `submitted`, and calls `pump_after_completions()` -> `swap(false)` returns `false`, skipping `pump_held_if_free` and leaving S2's held work un-woken.

Moving `COMPLETED.store(true, Ordering::Release)` to the end of `finish()` (after the `set_title_fence` loop) and pairing it with `COMPLETED.swap(false, Ordering::AcqRel)` in `pump_after_completions()` ensures any thread that consumes the flag is guaranteed to observe all writes and fence signals from `finish()` before pumping.
