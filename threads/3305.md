# Marvisak/VIctory#3305: gpu: refresh the submission's buffer copies on several threads

- PR by @borosf, opened 2026-11-26T16:38:57Z, state **closed**

- Archived copy; the original thread is authoritative while it exists.

## Description

## What

`Batch::flush` ran each pending copy's `Shadow::update` on the submitting thread, one after another. A world frame asks for ~80 copies moving ~265 MB through a single `ReadProcessMemory` thread.

Each copy appears at most once in the batch (`pending` is keyed by the shadow's pointer), so the updates touch disjoint state — `Shadow` is `Send + Sync` (shadow.rs:137-139) and holds its own locks; the copy itself is `ReadProcessMemory`, which is thread-safe. The flush now drains the refreshes and runs the updates through the existing `texture::in_parallel` (up to 4 threads, same helper the texture refresh uses). The `current`-range merge stays serial afterwards, in the original order, so its result is unchanged. `copystat`/`PREPARING` accounting is atomic and per-item, unchanged in meaning.

Claimed on #1633 (parallelize serial submission-prep buffer copies). Implemented at the `Batch::flush` level, across shadows — not inside `Shadow::update` — to stay clear of NEW-… partial-page-granularity work on that function.

## Measurement (Windows 11, Intel Arc B580 host, 12 cores, synthetic only — no game data)

New test `host::batch::many_copies_refresh_in_parallel_and_copy_the_same_bytes`: 16 write-watched pools x 64 pages (64 MiB), all pages dirty, one `Batch` holding all 16 copies:

```
cargo test -p victory-gpu --lib --locked -- --test-threads=1 --exact host::batch::many_copies_refresh_in_parallel_and_copy_the_same_bytes --nocapture
```

```
flush of 16 copies x 64 pages (64 MiB): parallel 6.547ms, serial 8.043ms
flush of 16 copies x 64 pages (64 MiB): parallel 7.117ms, serial 8.079ms
flush of 16 copies x 64 pages (64 MiB): parallel 6.514ms, serial 8.214ms
```

~1.2-1.3x on the pure copy path (same-process RPM already saturates ~8 GB/s single-thread on this host, so the synthetic ceiling is low); the test asserts the host copies hold exactly the title's bytes after both passes. On the real frame the per-copy kernel work that dominates (write-watch queries, soft faults on fresh snapshot buffers, the unmapped-page fallback walks) also runs inside `update`, so the ~927 ms copy phase of the 1,842 ms world frame is what this parallelizes across up to 4 threads — title-side number to be taken by whoever can run it.
