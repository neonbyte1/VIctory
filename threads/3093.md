# Marvisak/VIctory#3093: Shader tests: share one D3D12 queue per adapter

- PR by @neonbyte1, opened 2026-11-26T07:30:05Z, state **open**

## Description

Split out of #2973, as asked in its review: this changes how every `victory-shader` GPU test runs, Windows included.

The shader tests made a D3D12 device and a command queue for every test. They now share one device and one queue per adapter for the whole test process, and each test waits for its own work to finish, as before.

**Why:** under Wine/vkd3d-proton, `victory-shader`'s test process was killed with SIGKILL at exit: hundreds of queues were still being torn down when the process ended. With one queue per adapter it exits normally.

**Tested** (Linux, GE-Proton11-14 Wine, RTX 5090): `victory-shader` tests under `cargo xtask wine-test` (#1218), 298 passed, 4 failed, no SIGKILL. All four failures happen on `main` without this change too:
- `rounding_matches_the_hardware` is fixed by #2968.
- `stub_pipeline_is_created` is tracked in #1266.
- `hosts_that_do_not_fuse_are_named` and `a_heap_buffer_read_where_no_buffer_view_is_reads_zeros` are fixed by #2973.

**Not tested on Windows:** I have no Windows machine. A run of `cargo test -p victory-shader --lib` on a Windows GPU, and once with WARP, would close that gap. A test that left the queue in a bad state would now affect the tests after it; on this run none did.

The wall-clock improvement on real hardware is huge! Tested locally on Windows 11 (RTX 5090, running the `victory-shader` lib suite excluding the pre-existing `heap_direct_texture_reads_mark_their_heap_index` crash):
- Base `63bcca43`: **523.12s** (298 passed, 3 pre-existing failures)
- This PR `dc56cd73`: **33.56s** (298 passed, same 3 pre-existing failures) — a **15.6x speedup**, and concurrent submission is sound on the happy path because each call owns its own allocator, command list, resources, and fence.

However, caching the hardware `(device, queue)` permanently in a `LazyLock` introduces a few correctness issues in `crates/victory-shader/src/emit/host.rs`:

1. **`Host::new(false)` permanently returns a removed device after `DEVICE_REMOVED` (`emit/host.rs:183-188, 206-224`)**: Once `HARDWARE_DEVICE` initializes to `Ok(...)`, any subsequent `Host::new(false)` clones and returns the same device/queue even if the GPU has since entered `DEVICE_REMOVED`. Previously, `create_device(false)` surfaced device removal when callers like `emit/semantics_tests.rs:577-585` requested a fresh `Host` after a failure. Please check `GetDeviceRemovedReason()` on construction (and decide/document whether an initial creation failure should stay cached forever).
2. **`pub device` can diverge from the private cached `queue` (`emit/host.rs:17-20, 191-195, 215-234`)**: `Host.device` is `pub`, so replacing it leaves the cached `queue` bound to the old device while `fuses_fmad` / `draw` / `dispatch` create allocators, lists, and fences on the new device. Keeping `device` and `queue` paired behind read-only access (or rebuilding the queue when the device changes) prevents mismatched-device submissions.
3. **Fence completion loops treat `UINT64_MAX` (`DEVICE_REMOVED`) as success in `fuses_fmad` and `dispatch` (`emit/host.rs:751-763, 2011-2023`)**: `draw` checks `GetDeviceRemovedReason()` after exiting the wait loop (`:1285-1288`), but `fuses_fmad` and `dispatch` only check it inside `while fence.GetCompletedValue() < 1`. On `DEVICE_REMOVED`, `GetCompletedValue()` returns `u64::MAX`, exiting the loop immediately and mapping incomplete readback data. Now that a removed device is shared across tests, sharing a single completion-check helper across all three paths is much more important.
4. **Hardware concurrency coverage**: The new test (`:2055-2097`) currently exercises the serialized `WARP_LOCK` path. Adding a hardware-path concurrency test (when not forced to WARP) with distinct per-thread readback payloads would directly cover the concurrent queue path this PR enables.

Thanks for the Windows hardware run and the four points. All four are addressed in a follow-up commit, `deedac2`:

1. **Removed device.** The cached hardware (and WARP) device and queue sit in a mutex as one pair. `Host::new` checks `GetDeviceRemovedReason()` and, if the cached device is removed, drops the pair and makes a new one.
