# Marvisak/VIctory#3378: GPU: the dropped passes a presented image reads go first in the pipeline queue

- PR by @neonbyte1, opened 2026-11-26T20:58:35Z, state **open**
- <https://github.com/Marvisak/VIctory/pull/3378>
- Archived copy; the original thread is authoritative while it exists.

## Description

**Stacked on #3353** (`fix/hold-unwritten-frames`, `df15a809`); only the last commit (`dba19ba2`) is new here.

## What is wrong

#3353 fixes the flicker while pipelines are still being made: a dropped draw into the presented image holds the frame and its pipeline goes to the head of the workers' queue. A dropped pass *further back* still leaves the image wrong, because the image is then written from stale inputs.

Grand Theft Auto VI's world on a cold driver cache (`__GL_SHADER_DISK_CACHE=0 VKD3D_SHADER_CACHE_PATH=0`, RTX 5090, Wine + vkd3d-proton) first binds ~1,900 pipelines in one frame. With #3353, the final upscale is made at once. But the world then stays black (brightest probed pixel 0–1 of 255) until the compute pass that resolves the lighting (`structure_lod_wetness:CS_RaytracingResolve`) is made. That pass waited **47–54 s** in the queue in three runs, and then took **5.8–6.1 s** to build. The image turns bright on the first frame after both pipelines exist, while ~1,000–1,700 others are still queued.

## What changes

While pipelines are queued, each frame notes:

- **for passes that run:** what each reads and writes (the views its code uses through tables, its render targets and depth);
- **for passes that are dropped:** what each would have written:
  - its targets;
  - the unordered views its code names through tables. These come from the container's own resource records, so no translation is needed.

At the present, a walk goes back from the presented images through passes that ran. It finds the dropped passes whose writes those passes read, and the nearest ones go to the head of the workers' queue (`crate::feeds`). Once a hurried pass runs, a later frame's walk goes on behind it.

The walk must not take the world's content. A first version did: one round put **666** mesh pipelines first and pushed back 103 pipelines the queue would have made within 15 s (a TAA resolve, a tiled-lighting clear, decal and particle compute). The world went dark again for about a minute. Hence three limits:

- **Reads are kept per pass, not per pipeline.** A pipeline many passes share (a blit) would otherwise join every one of their inputs.
- **A resource with more than 4 dropped writers is not followed to them** (`FAN_IN_MAX`). One or a few passes (a resolve, lighting) leave a resource stale; hundreds of draws into depth or a geometry buffer leave objects missing. The walk still goes *through* such targets' passes that ran.
- **At most 8 pipelines per present** (`HURRY_MAX`), nearest first. Only pipelines that can still be hurried count toward the 8: queued, not taken by a worker, not hurried before.

The first 64 pipelines a run hurries (`FIRST_MAX`) are listed in `first-pipelines.txt`, beside `early-pipelines.txt`. The next run starts them ahead of the other early starts, during loading.

The code names no shader.

## Limits

- Buffers and views a shader indexes in the heap itself are not followed; only descriptor-table views and targets are.
- A pipeline first bound only after the backlog (the lighting resolve in hurry3/4) is hurried at once but still takes its build time. The list only helps pipelines a run actually hurried.
- With the list loaded, a boot-screen pipeline was held for 2 frames: it was hurried early and the hold waited for it. The hold limit (10 s, #3353) bounds this.
- Passes are taken per frame in the order they were recorded on any thread. A pass may be counted as feeding the image even though it runs after the read; that only moves a pipeline ahead in the queue.

## Cost

When nothing is queued (a warm run, or once the queue drains):

- **Per bind:** one relaxed atomic load and a thread-local flag.
- **Per view and per pass that runs:** a flag test. No lock, no map.
- **Per dropped pass:** one `OnceLock::get`. Refused pipelines stop there. A container's resource records are parsed only for pipelines being made, once per container.
- **Per present:** one uncontended lock and `mem::take` of an empty graph, which allocates nothing.

While pipelines are queued:

- **Recording:** one mutex per pass that runs, and set inserts per view and target.
- **The walk:** once per present, only if a dropped pass was noted.
- **Memory:** everything is per frame. The graph is dropped at each present and capped at 2^20 notes per frame (`NOTES_MAX`). `first-pipelines.txt` is capped at 64 keys.

### Review (CHANGES_REQUESTED) by @fuzeofficlal — 2026-11-26T21:21:38Z

<https://github.com/Marvisak/VIctory/pull/3378#pullrequestreview-6080585193>

The pass-level feeder graph (`feeds.rs`), `FAN_IN_MAX`/`HURRY_MAX` bounds, lock-free warm fast path, and `first-pipelines.txt` persistence are cleanly designed and well-tested (all 62 `feeds`/`shown`/`pipeline`/`draw` tests and strict `clippy` checks pass on both RTX 5090 and WARP with `VICTORY_D3D12_DEBUG=1`).

However, auditing the new hooks turned up one live crash bug and two graph-tracking bugs that should be fixed before merge:

### 1. Blocking: `State::not_made` dereferences unchecked descriptor table pointers without `self.heap_of` (`crates/victory-gpu/src/draw.rs:628-633`)
```rust
for u in uavs {
    if let Some(&Root::Table(table)) = self.roots_ref(compute).get(usize::from(u.slot))
        && let Some(View::Unordered(resource, _, _)) =
            crate::descriptor::view(table + u64::from(u.table_offset_dwords) * 4)
    {
        writes.push(resource);
    }
}
```
Unlike `State::table_entry` (`draw.rs:1236`) and `State::tables` (`draw.rs:1270, 1297`), which always verify `self.heap_of(handle)` before reading title descriptor memory, `State::not_made` computes `table + u64::from(u.table_offset_dwords) * 4` directly and passes it to `descriptor::view(handle)`. Inside `descriptor::view` (`descriptor.rs:558-563`), any non-zero `handle` is immediately dereferenced via `(handle as *const [u32; 3]).read_unaligned()`.

If a title binds a null root table (`Root::Table(0)`), has no bound view heap, or leaves a stale root table handle from an earlier released/unmapped heap, and `u.table_offset_dwords > 0`, `table + offset` produces a non-zero invalid address (e.g. `0x20`) and immediately crashes with an access violation. (Unchecked `table + offset` can also overflow `u64`.)

- **Reproduced live on Windows**: calling `state.not_made(true)` on a pending compute pipeline (`being_made == true`) with one table UAV at `table_offset_dwords = 8` and `state.set_table(true, 0, 0)` crashed the child process with **`0xC0000005` (`STATUS_ACCESS_VIOLATION`)**.
- **Fix**: validate with `checked_add` and `self.heap_of(handle)`:
  ```rust
  if let Some(&Root::Table(table)) = self.roots_ref(compute).get(usize::from(u.slot))
      && let Some(handle) = table.checked_add(u64::from(u.table_offset_dwords) * 4)
      && self.heap_of(handle).is_some()
      && let Some(View::Unordered(resource, _, _)) = crate::descriptor::view(handle)
      && resource != 0
  {
      writes.push(resource);
  }
  ```

### 2. Null SRVs / UAVs (`resource == 0`) create a phantom hub node in `feeds::Graph` (`crates/victory-gpu/src/draw.rs:632, 1928-1936`, `crates/victory-gpu/src/feeds.rs:81-105, 166-195`)
`descriptor::create_srv(NULL, ...)` and `create_uav(NULL, ...)` record `View::Shader(0, _)` and `View::Unordered(0, _, _)`. While `feeds::ran` and `not_made` carefully skip `depth == 0`, neither `readable`, `not_made`, nor `feeds` filters out `resource == 0` (nor `0` in `targets`/`writes`).

Because `Graph::ran[0]` has no `FAN_IN_MAX` cap, any pass feeding a presented image that binds a null SRV (`0`) walks through `Graph::ran[0]` into every unrelated ran pass that bound a null UAV (`0`), pulling unrelated dropped pipelines into the priority queue.
- **Reproduced in `feeds::tests`**: `g.dropped(99, || "unrelated_dropped", &[unrelated_tex]); g.ran(&[unrelated_tex], &[0]); g.ran(&[0], &[image]);` returns `feeders = ["unrelated_dropped"]`.
- **Fix**: ignore `0` resources in `feeds::view`, `feeds::ran` (`targets`), and `feeds::dropped` (`writes`) (or inside `Graph::ran`/`Graph::dropped`).

### 3. `Graph::ran` bypasses `NOTES_MAX` when `writes.is_empty()` (`crates/victory-gpu/src/feeds.rs:81-91`)
When a pass runs with `writes.is_empty()` (e.g., a bindless/root-view-only compute dispatch), its index is never inserted into `self.ran`, so `self.reads.push(...)` stores an unreachable entry; when `reads.is_empty()` as well, `self.notes += 0` never increments, letting `self.reads` grow past `NOTES_MAX` unboundedly if presenting pauses while pipelines are queued (`10_000` calls -> `notes = 0, reads.len() = 10_000`).
- **Fix**: early-return in `Graph::ran` with `if writes.is_empty() || self.notes >= NOTES_MAX { return; }` (mirroring `Graph::dropped` at line 96).
