## What

#233 runs console wave64 compute programs on hosts without 64-lane waves (NVIDIA) as two 32-lane waves, in the "console flow" where a program needs its whole wave. It still stopped programs that share LDS inside one wave, and a few other forms. This PR takes those:

- **One console wave sharing LDS without `s_barrier`.** The console runs an instruction in all 64 lanes before the next, so a lane reads what another lane wrote one instruction earlier. In the console flow both halves reach every LDS access together, so a group barrier before each access puts it after every earlier one.
- **Whole-wave sections** (reductions and prefix sums) in groups of exactly 64 threads: each half's result is exchanged and combined, integers and floats.
- **`ds_bpermute_b32`**, which did not translate on any host: a read within the lane's own 32-lane half.
- **Selects on masks held as numbers**, on every host.
- **Loop-carried mask joins** in the console structure.
- Refusals that say why (`... in a group of more than 64 threads`, `ds_permute across the halves`, `a whole-wave section`), and a `translate --validate` line that prints a failing module's thread-group size, wave size and `dx.op` names.

Nothing changes for programs that translated before, with two exceptions measured below: on hosts that run 64-lane waves about 18 title programs with a lane read in a divergent branch change from the per-lane form to the console flow, and programs both forms refuse may report a different reason.

## Validation note

Compute programs that sample with implicit derivatives (`image_sample`) are emitted as `dx.op.sample`, which validator 1.6 / 1.7 rules do not allow outside pixel shaders. `main` emits 23 such modules; this stack lets more such programs translate, so more of them appear (54 here). The cause is not in this stack: [diagnosis with a hand-assembled reproduction](https://github.com/Marvisak/VIctory/pull/233#issuecomment-7121852191). #180 replaces these samples and #201 tracks the class; a [census rerun](https://github.com/Marvisak/VIctory/issues/201#issuecomment-7122527604) measured #180 taking the class to 0 on `main`. Merging #180 first, or together, keeps those modules from reaching a driver unvalidated.

## How this relates to other open PRs

- #189 and #192 also order single-wave LDS with barriers, in the per-lane form: they analyse where a barrier is needed and legal. In the console flow every block is reached by the whole group, so a barrier is legal before every access and no analysis is needed; the cost is a barrier per LDS access. #189 also handles LDS in groups of several console waves, which this does not. The two approaches conflict in the same code; a tree carries one or the other.
- #578 refuses pipelines whose emitted module needs a wave size the host lacks. Since its follow-up it checks the emitted `PSV0`, so it does not refuse what this stack emits.

## Not verified

- No console hardware. Expected values in the tests follow the ISA's semantics. Why `ds_bpermute_b32` stays in each half: AMD, *"RDNA 2" Instruction Set Architecture Reference Guide* (30 Nov 2020), §10.4.4 "LDS Lane-permute Ops", pp. 96–97: "in wave64 mode the permute operates only across 32 lanes at a time of each half of a wave64 … it executes as if were two independent wave32's. Each half-wave can use indices in the range 0-31 to reference lanes in that same half-wave", "only index bits [6:2] are used", "Reading from disabled lanes returns zero". The lowering follows this (lane `((addr + offset) >> 2) & 31` in the reader's half, 0 where it is inactive). The opcode table's pseudocode (§12.13, p. 206) writes `mod 64`, which disagrees with §10.4.4; we follow §10.4.4. `ds_permute_b32` is not translated yet and still keeps a program out of the split.
- Nothing after `f653ea4` has been run in the title, by anyone. The local run only translates and validates.
- What the barriers and guards cost on real dispatches, beyond the one frame-time figure above.
- A float sum across the halves adds each half's sum last: one more order of additions, so its last bits may differ, as they already may within one host wave.
- Of the LDS tests, one needs the barrier before each LDS access on an RTX 5070 (masked write and masked read with no branch between: the lower half reads 0 in 20 of 20 runs without it). The others pass either way on that card, so they check the result and not the need.
- Masks copied dword by dword (EXEC restored with two `s_mov_b32`) stop with a reason; following them is not done.

- **Whole-wave sections:** each half reduces its own lanes with a wave op over the masked inputs, then the halves trade results through `exchange`. A reduction combines the two. A prefix adds the lower half's total in the upper half (`Lower::console_shape`). It covers integer and float sums, min, max, and/or/xor; f16 is refused.
- **Eligibility:** LDS and sections are allowed, and permutes only inside sections. A group of one console wave that shares LDS without lane reads also takes the console flow.
- **Title memory:** the extension applies only to programs that don't reach title memory by address (`root_memory`). Without that limit, the builder stages `caa78b8ca62bc3d6` and `28918b7150a7aad5` translated, part of the builder ran, and the GPU hung.

#320 and #439 cover the same ground. Your LDS barrier comes before each access, and your sections now handle partial groups and f16. So this is more for comparison than to merge as it is.
