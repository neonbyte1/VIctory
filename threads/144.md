# Marvisak/VIctory#144: Wine + vkd3d-proton on NVIDIA: the driver crashes in vkCreateComputePipelines while the world loads (0xc000001d / 0xc0000005, earlier stack overflows)

- Issue by @ItsYusei99, opened 2026-11-24T00:57:36Z, state **open**
- <https://github.com/Marvisak/VIctory/issues/144>
- Archived copy; the original thread is authoritative while it exists.

## Description

Under Wine with vkd3d-proton on an RTX 4070, the menus run, but loading into the world kills the whole process inside the NVIDIA Vulkan driver while it compiles one of the title's compute pipelines. VIctory logs nothing (no `crashes.log` entry); the only trace is Wine's message for the Unix call.

### Environment

- CachyOS, kernel 7.3.4; Wine 11.22 (system `wine` package)
- NVIDIA GeForce RTX 4070, driver 620.70.06 (`nvidia-open-dkms`)
- AMD Ryzen 7 9800X3D, 30 GB RAM
- DXVK `dxgi.dll` v3.1.1-134 (from GE-Proton11-11)
- VIctory Windows build via `cargo xwin` (rustc 1.98.1), run with `wine victory.exe run …\game_scarlett_master.exe --execute --console series-x`
- Input with a DualSense through Wine's SDL backend; menus navigated by hand

### What happens

The menus reach the world load (`story000*.rpf` opened, mesh pipelines made). Then, while pipelines are being created:

**1. `main` 35b054e, vkd3d-proton 3.1.0 (GE-Proton11-11):** illegal instruction in the driver right after one compute shader is translated:

```
INFO victory_gpu::pipeline: shader translated stage="compute" hash=8bb272e763f76148 user_data=1 samplers=0
0214:err:vulkan:vkCreateComputePipelines Exception 0xc000001d in Unix call.
```

**2. Same build:** in another run, stack overflows on four threads at one Unix-side address. One of them was vkd3d-proton's pipeline-library disk thread. The overflowing threads had 1 MiB stacks, which is the executable's default reserve:

```
01c8:err:virtual:virtual_setup_exception stack overflow 1792 bytes addr 0x6f44ef27e623 stack 0x10da4c0900 (0x10da4c0000-0x10da4c1000-0x10da5c0000)
01d0:err:virtual:virtual_setup_exception stack overflow 2304 bytes addr 0x6f44ef27e623 stack 0x10da8e0700 (0x10da8e0000-0x10da8e1000-0x10da9e0000)
01d8:err:virtual:virtual_setup_exception stack overflow 2880 bytes addr 0x6f44ef27e623 stack 0x10dcd604c0 (0x10dcd60000-0x10dcd61000-0x10dce60000)
0170:err:virtual:virtual_setup_exception stack overflow 2944 bytes addr 0x6f44ef27e623 stack 0x10d6870480 (0x10d6870000-0x10d6871000-0x10d6970000)
```

**3. `main` 9aef3d9 plus a 16 MiB default stack (see the linked PR), vkd3d-proton 3.2.0 (Proton Experimental 11.0-20261112):** the stack overflows are gone. The driver now faults with an access violation instead:

```
020c:err:vulkan:vkCreateComputePipelines Exception 0xc0000005 in Unix call.
```

At that moment the only compute shaders that were translated but had no host pipeline yet (made or refused) were `690e2883f9dd25d8` and `a3d1a26ad0c8c2cd`.

### Other observations from the same runs

- With the vkd3d-proton builds from Proton Hotfix and Proton Experimental, `8bb272e763f76148` compiles without the illegal-instruction crash. With 3.1.0 it does not. So the crash depends on the vkd3d-proton version, and probably also on the SPIR-V it emits for that shader.
- Many world compute pipelines are refused (`Required WaveSize range [64, 64], but supported range is [32, 32]`), as expected on NVIDIA. Some pixel/compute shaders do not translate: 64-bit image atomics, sub-dword LDS writes, addresses not from root parameters, barycentrics, and descriptors read as data. None of those kill the process.
- In the run that stayed alive the longest, the last frame lines show the loading screen at 18–27 fps.

### Not tested yet

- `VICTORY_SKIP_PIPELINES=690e2883f9dd25d8,a3d1a26ad0c8c2cd,8bb272e763f76148` (diag build), to see whether the load gets past this point or the fault moves to another shader.
- Another NVIDIA driver branch.

I can provide the full logs, run the diag build with any variables you want, or try patches. The translated DXIL of the shaders above is in the shader cache if that helps.

**Both crashes traced on an RTX 4080: the first is a vkd3d-proton converter bug fixed upstream on 2026-11-04, the second is #177**

Same symptoms here on another NVIDIA card: RTX 4080 16 GB, driver 620.73.04, Arch-based Linux (kernel 7.3), Core i5-13600K, GE-Proton11-12's Wine, release build cross-compiled on Linux, Series X 1.0.2.1.

**1. `0xc000001d` at `8bb272e763f76148` (older vkd3d-proton)**

3 of 3 load-ins on `97c78d1` and `35b054e` with GE-Proton11-12's vkd3d-proton `8293130eb`. In the run I traced, the fault is a `ud2` at `libnvidia-gpucomp.so.620.73.04 + 0x3c94c0`, reached from `vkCreateComputePipelines`, so the driver's compiler is trapping on purpose.

The SPIR-V it was handed is invalid, and the DXIL is not at fault: the same DXIL converts cleanly with a newer converter. With `VKD3D_SHADER_DUMP_PATH` set, 2 of 38 dumped modules fail `spirv-val`; the last compute module written before the crash ends in a block with no terminator ("Function end cannot be called in blocks"), and the other is the `23f68a442af34984` that a Mesa tester reported in #49 ("exits the loop ... but not via a structured exit").

I built the dxil-spirv CLI at the commits each vkd3d-proton carries and converted the 337 DXIL entries then in VIctory's shader cache (two builds, so some programs count twice), checking with `spirv-val --target-env vulkan1.3 --scalar-block-layout`:

| dxil-spirv | Carried by | Valid | Invalid | Converter crashed |
|---|---|---|---|---|
| `8b48f0e0` | vkd3d-proton `8293130eb` (GE-Proton11-12) | 310 | 24 | 3 |
| `114e664e` | vkd3d-proton `2576c0b4a` (Proton Experimental 11.0-20261112) | 335 | 2 | 0 |
| `34f0ff84` | vkd3d-proton master | 335 | 2 | 0 |

A bisect over the two dumped DXIL files lands on dxil-spirv `71967a38`, "Rewrite the structurizer from scratch" (2026-10-27). The first vkd3d-proton commit that carries it is `256f751018` (2026-11-04). So vkd3d-proton builds from before that date carry the old structurizer and break on some of these shaders; builds from that date on convert them. That matches the report above: 3.1.0 crashes, the Hotfix and Experimental builds do not.

With `2576c0b4a` in a copy of the same prefix, the pipeline for `8bb272e763f76148` builds and loading goes on.

**2. `0xc0000005` at world entry (current vkd3d-proton)**

This one is VIctory's, and #177 fixes it. The 2 modules that stay invalid in the table above are atomics with a `%float` result type: the heap-handle cache hands an image atomic the float handle of an earlier load of the same image.

It is wider than the shaders named so far. Translating the whole package offline (`victory translate --list` with `VICTORY_EMIT_DUMP`) and converting every emitted DXIL with dxil-spirv `114e664e`:

| Build | DXIL emitted | Invalid SPIR-V |
|---|---|---|
| main `d2a4bae` | 22,151 | 39 |
| #177 `e55eb69` | 22,151 | 0 |

The 39 are 13 compute and 26 pixel programs (22 `AtomicUMin`, 11 `AtomicOr`, 3 `AtomicUMax`, 3 `AtomicIAdd`). The pixel ones would explain the faults moving to `vkCreateGraphicsPipelines` once a compute shader is skipped. #177 changes the DXIL of exactly those 39 programs and of no other.

In the game: on `9aef3d9` I get the same `vkCreateComputePipelines Exception 0xc0000005`, and `a3d1a26ad0c8c2cd` was among the shaders translated with no pipeline result at that moment, as in the report above. With the same key change as #177 applied, one run had no driver trap, translated 577 shaders and reached the opening cutscene. It stopped there on a GPU fault (kernel `Xid 13 ... MMU Fault`), which is a different problem.

I have not mapped the 39 programs to the 16-digit hashes people have named, so I cannot say that each of those hashes is one of them. Running #177 is the direct check.

I did not see the stack overflows from case 2 in any run.

### Comment by @andyeox-systemd — 2026-11-25T18:58:53Z

## Found the cause, and a fix: #2723

The crash in `vkCreateComputePipelines` on NVIDIA under Wine has two separate causes. I dumped every shader with `VKD3D_SHADER_DUMP_PATH` and checked it with `spirv-val`.

1. **vkd3d-proton 3.1 and earlier:** dxil-spirv's old structurizer emits invalid control flow for three shaders ("Function end cannot be called in blocks", "block exits the loop headed by…"). Microsoft's `dxv` accepts VIctory's DXIL for all three, so it's a converter bug. It's fixed in **vkd3d-proton master**, which has the new dxil-spirv structurizer. It is not in 3.1.
2. **VIctory:** a UAV read as float and also used by an atomic got one float-typed handle, which becomes an invalid `AtomicOr` / `AtomicUMax` in SPIR-V. #177 fixed one handle cache. `main` has since added two more with the same problem, and #2723 fixes all three.

With both fixes (RTX 4070 Ti, driver 620.73.04, Wine 11.22, vkd3d-proton master), there is no crash, all 1,277 dumped shaders are valid SPIR-V, and the title reaches the first cutscene at 0.2 to 0.7 fps, with the 3D scene black as in other reports. With vkd3d-proton master but without #2723, it still crashes, with 2 invalid atomic shaders.

So NVIDIA users on Wine need vkd3d-proton built from master (or the next release) plus #2723.
