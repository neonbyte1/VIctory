# Marvisak/VIctory#346: GPU: expand indirect rectangle-list draws on the GPU

- PR by @BastienRodz, opened 2026-11-24T02:28:28Z, state **closed**

## Description

Closes #255 for non-indexed draws.

## What

Indirect draws with the console's rectangle-list topology (17) now run on the host instead of being dropped. `State::execute_indirect` refused them because rectangles are expanded on the CPU (`primitive::expand_rects`), and an indirect draw's vertex count is only known on the GPU. #255 counts about 250 of these drops per world frame, and the title draws its full-screen passes as rectangles.

## How

For kind 0 (`DRAW`) with `RECTANGLES`, after the existing argument clamp, two compute passes of ours run before `ExecuteIndirect` (new module `crates/victory-gpu/src/rectangles.rs`). Both are HLSL compiled at run time by the system's `D3DCompile` (cs_5_1): Microsoft's, or Wine's vkd3d-shader under Wine/Proton. For the latter they read buffers as 32-bit words (`(RW)StructuredBuffer<uint>`), and their root signatures are serialized in code (since `c256f83`; checked with vkd3d-compiler 2.1, the version GE-Proton11-12 ships).

1. **`rect_rewrite`** (one thread per record):
   - Respects the title's count buffer.
   - Checks that `start .. start + 3 * rects` lies inside every bound per-vertex vertex buffer.
   - Allocates `rects * 6` vertices from a per-list scratch with an atomic counter.
   - Writes a rewritten copy of the record into a list-owned arguments buffer: `rects * 6` vertices, the same instances, the allocated start, the same start instance.
   - The title's arguments are not changed beyond what the clamp already does.
2. **`rect_expand`** (one group per record, one pass per per-vertex slot):
   - Writes `(v0, v1, v2, v0, v2, v3)` per rectangle.
   - Computes `v3 = v0 + v2 - v1` the way `expand_rects` does: same formats (`primitive::components`), same half-float and UNORM conversions and rounding. Unknown formats and components past the stride keep v0's bytes.
3. `ExecuteIndirect` then reads only list-owned buffers: the rewritten arguments, in which records at or past the title's count are empty draws, so no count buffer is passed (since `7ff1184`). The expanded slots are bound with `IASetVertexBuffers`. Transitions around the draw put the scratch back in unordered access, so the next indirect rectangle draw of the list reuses it.

Half floats, on both paths (`primitive.rs` and the shader's copy):
- halfway values round to even (`4090d29`): fuzeofficlal's fix for the direct path ([comment](https://github.com/Marvisak/VIctory/pull/346#issuecomment-7122043116), their `c256b97`), carried here since PR creation is limited to collaborators;
- subnormals as #418 writes them on the CPU (`1278485`).

The CPU and GPU paths therefore still agree byte for byte.

List-owned memory (`host.rs`):
- one 8 MiB default-heap vertex scratch per list, made on first use;
- a rewritten-arguments buffer that grows when a draw has more records;
- chunks of atomic counters, zeroed at submission the way the clamp's budget is.

`indirect::bound` is split so that `clamp_uav` (clamp, then a UAV barrier) can be followed by the rewrite pass. `bound` itself behaves as before.

Fallbacks: if a pass is unavailable or the arguments are unaligned, the draw is dropped as before, each case with its own diagnostics `why(...)` reason. Records that do not fit the scratch, or that reach past their buffers, draw nothing.

The rectangle path changes the state of no title buffer: the arguments and the count are only read, by the rewrite pass.

Limitations, written as `shortcut:` notes in the module:
- **Indexed rectangles:** still unsupported, as for direct draws. They get their own reason now.
- **Scratch size:** 8 MiB per list, shared by the records of one draw.
- **Fourth corner:** computed from vertex inputs, not vertex shader outputs, as in `primitive`.
- **Pipelines with no per-vertex inputs:** a pipeline that builds its corners from the vertex id gets `6 * rects` vertices from 0, the same as a direct rectangle draw today. The vertex-ID remap suggested in #255 is not part of this PR.

Reviewed `cee702e` and ran it on an NVIDIA RTX 5070 (driver 621.24), Windows 11: `cargo test -p victory-gpu` 50 passed, 0 failed, 1 ignored; all rectangle tests pass. I found no defect in the corner math, bounds, allocator or barriers. One ordering problem and a few questions:

**Rebasing onto #242.** The rewrite and expand passes read the title's own argument records after `clamp_uav` (the rewrite pass, and the expand shader again for `StartVertexLocation`), so they rely on today's clamp writing the clamped values back in place. #242 changes the clamp to read the source in place and write clamped records into a separate scratch buffer (`bound` returns `Bounded { scratch }`, no in-place variant). Since #242 is meant to land first, after the rebase both passes need to read #242's scratch records; reading the title's copy would bring back unclamped counts (`rects * 6u` can wrap, and a pipeline with no per-vertex inputs is then unbounded in count and instances).

**Half floats.** `f32_to_half` in the expand shader combines the rounded mantissa with `|` (`sgn | (ex << 10) | ((man + 0x1000) >> 13)`), the same pattern #260 fixes in `primitive.rs` (a rounding carry is lost when the exponent is odd, e.g. 1.99995 gives 1.0). CPU and GPU agree today, so not a regression, but the shader will need the same change when #260 lands or the two paths diverge.

Questions:
- The rectangle path moves the title's count buffer between `UNORDERED_ACCESS` and `INDIRECT_ARGUMENT`, while the non-rectangle path in `draw.rs` does not transition it. If one list uses a separate count buffer on both paths, one of them sees it in the wrong state. Worth a check with the debug layer once a count-buffer title draw shows up.
- The title's vertex-buffer copies are bound writable in the expand pass although they are only read. If an earlier draw in the same list read one as a vertex buffer, it was promoted to a read state, and a read state cannot be promoted to unordered access. A `ByteAddressBuffer` view would avoid that.
- `StartVertexLocation` comes from an atomic allocation, so its order can change between runs; a vertex shader reading `SV_VertexID` alongside inputs would see different IDs than on the direct path. The `shortcut:` notes cover only the no-input case.
- The 8 MiB per-list vertex scratch is never released.

The GPU test drives both shaders with hand-written constants and does not go through `expand()`, so the barrier sequence, slot layout, counter reset and argument-buffer growth have no test. I tried a temporary case through the shaders with an 11-byte stride, data starting 3 bytes in, unaligned f32/half/unorm16 attributes and two records: the GPU output matched `expand_rects` byte for byte.

**A workaround for the `title+0x4dcbc9d` assert that otherwise blocks every PR test here**

Following the control result above (main `97c78d1` and head `0aebe86` both died at `+0x4dcbc9d`), we RE'd the assert and can now get past it deterministically, which may help other testers reach the world.

The assert is a **title-side packet stream**, not a GPU command buffer. At `+0x4dcbc9d`, `rcx` is a 40-byte slot: `desc*`, `dataBase*`, capacity `+0x10`, cursor `+0x18`, watermark `+0x1c`, stream id `+0x20`.
