# Marvisak/VIctory#747: NVIDIA capped view heap: 2^16 dynamic slots starve world tables; 2^18 removes the indirect/mesh drops

- Issue by @Vaximous, opened 2026-11-24T09:27:33Z, state **open**
- <https://github.com/Marvisak/VIctory/issues/747>
- Archived copy; the original thread is authoritative while it exists.

## Description

On NVIDIA the shader-visible view heap is capped at 1,000,000. An RTX 4070 Ti on binding tier 3 refuses 1,000,001, so a bigger heap is not an option. `HostHeap::new` then falls back to `MIN_DYNAMIC = 1 << 16` dynamic slots (`crates/victory-gpu/src/descriptor/host.rs`). With GPU-driven world rendering that pool runs dry inside every submission. Most of the world's indirect draws and mesh dispatches are then dropped as "a descriptor table without dynamic slots", which leaves the G-buffer nearly empty. The comment on `DYNAMIC` already notes that 2^16 ran out on an RX 9070 XT (#59). On a capped heap that is still the amount it gets.

## Measured (RTX 4070 Ti, Windows 11, title build 1.0.2.1, local integration branch = main + many open PRs)

- The title's view heap has 1,245,184 slots. It writes about 1.1M of them, and its tables reach the top of the heap.
- Tables that must be made fresh (constant buffers, or tables past the mirrored range) need **about 300-550k slots per 5 s**, against 65,536 dynamic slots. The existing per-list dedupe of fresh tables hits only 10-15%.
- Per frame in the world, with the 2^16 split: indirect kind 10 (mesh) about 410-670 dropped, kind 2 (dispatch) about 480-540, kind 0 rectangles about 190-200, kind 1 about 60, plus about 280 direct draws/dispatches. All for "no dynamic slots".
- **With 2^18 dynamic slots on the capped heap** (672,319 title slots mirrored): zero "no dynamic slots" drops, and no table refused as past the heap. Indirect drops fell from 1,484-1,768 to 322 per frame on average; the 322 left are shaders that don't translate. Draws run per frame went from about 1,460 to 2,690. G-buffer coverage at a 2,000-draw frame of the first cutscene went from about 0.1% to 60-65% (terrain, cliffs, characters).

## Proposed change

`MIN_DYNAMIC = 1 << 18` (or the capped path uses `DYNAMIC`). The cost is that bindless reads of title indices above about 672k land on the null/guard slot instead of above about 869k. In this title no draw was refused as past the heap after the change.

A second, independent saving: a fresh table only needs slots from the first entry its shaders actually use, not from entry 0. Large tables (more than 64 entries, about 140 slots each) where shaders read a few entries made up about 90% of the demand.

I have this on a local branch with tests (`a_reserve_keeps_dynamic_slots_for_required_tables`, `fresh_tables_start_at_their_first_used_entry`). I can't open a PR while PR creation is limited to collaborators, but I'm happy to provide the diff.

Related: #16 (1M heap cap on NVIDIA), #336 (2^18 dynamic slots where the heap fits), #735 (a 1.31M heap on an RTX 4060 Laptop).

### Heap layout

[`view_layout` implementation](https://github.com/AimLogin/VIctory/blob/cc449ca941abea558dc56271c10f7ce0459ab66a/crates/victory-gpu/src/descriptor/host.rs#L133)

- A host that accepts `count + 2^18` retains the existing heap split.
- On a host capped at 1M, a title heap that fits with at least 2^16 slots to spare keeps every title slot, with the remaining space assigned to the dynamic range.
- The world's heap (1,245,184 requested title slots) gets **737,856 title + 262,144 dynamic** instead of 934,464 + 65,536.
- With the second commit, the last 21 dynamic slots are reserved as typed guards, leaving 262,123 allocatable dynamic slots.
- A host capped above 1M that accepts `count + 2^16` keeps the old split if the larger allocation fails.

The difference from the alternative layouts linked here is that uncapped hosts and title heaps that fit are not unnecessarily cut. A test checks the new split against a copy of the old implementation for caps of 900k, 1M, 1.31M, 1.4M and no cap.

### Why it should land together with a bindless bound

Direct heap reads (`ResourceDescriptorHeap[i]` with a title index) are not bounded on the tested `main` revision.

On a 1M-capped host, title indices at or above the title-slot count can read dynamic slots holding other draws' tables. With this layout, that window starts at 737,856 instead of 934,464, the concern @desplmfao raised above.

A synthetic GPU readback test demonstrates such an access writing into another draw's UAV on both the RTX 4060 Ti and WARP.

The second commit bounds direct title accesses to the title-slot range and redirects out-of-range accesses to typed null guards. Table-rooted accesses remain bounded by the guard base, not by each individual table's length.

This builds on @Vaximous's guard scheme in #483. Further integration details are documented in the linked patch.

### Known limitations

- No world run of my own.
- No AMD hardware validation.
- No count of how often the title reads past the available title slots.
- Out-of-range title reads return null rather than recovering the intended resource.
- Root signatures already near 64 dwords may still be refused; #644 is a complementary approach.
- As @undeadhuman37 reported, the extra slots alone eliminated descriptor exhaustion in their test but did not eliminate the NVIDIA world hang. Wave64 compute remains a separate problem.

The patch is offered for review, integration or cherry-picking, whichever the maintainers prefer.
