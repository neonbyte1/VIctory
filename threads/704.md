## What

#193 lets a program whose structured buffer has no stride known at translation read it through a raw (`ByteAddressBuffer`) handle, at a byte offset computed from a run-time stride table. Four reviewers showed that this returns wrong data on NVIDIA whenever the heap slot holds a structured or typed view, which is what a title's structured buffer is: the raw handle resolves to the view the title made, not to a raw view.

This PR makes the read go through a raw view of the same bytes, so the handle's kind always matches the view it resolves to.

- **The table entry is two dwords** (`StrideEntry`): the stride, then the heap slot that holds a raw view of the same bytes (plus one; 0 means the slot itself is raw), with a 4-bit byte bias on top.
- **Shader side.** The program reads the entry by the heap slot it computes at run time, the same value the handle used to be made from, then makes a raw handle of the named slot and accesses `index * stride + offset + bias`. Loads, stores and atomics share the path.
- **GPU side.** Whenever `HostHeap` makes a structured or typed buffer view (SRV or UAV), it also makes a raw view of the same bytes in a pool of 65,536 slots after the dynamic ones, and writes the entry. Raw views keep their own slot. Remaking a slot reuses its pool slot; a null, raw or constant view, or a released dynamic slot, returns it. The entry is written wherever the slot's descriptor is written, so it is as current as the descriptor.
- **The bias** exists because a host raw view must start on 16 bytes and the console's can start on any dword: the raw view starts up to 12 bytes early.
- A read past the view's element count reads zero: the raw view ends where the title's view does.
- **Release order** (`4e03086`, from r4tedx/VIctory#7): when a list gives its dynamic slots back, their table entries and raw views are cleared before the slots are marked free. `30a93f9` did it the other way round, in two separate lock scopes, so another list could lease a slot, write its entry, and have it wiped by the retiring list. `fb8ea43` (from r4tedx/VIctory#8) tests it without a scheduler race: it leases the whole dynamic pool, then asks the allocator for a slot at the start of the last slot's cleanup, which must fail until the cleanup is done. With the old order restored the test fails here (the slot is leased during cleanup); with the fix it passes.

## Why not pick the handle kind in the shader

That was the first design tried, and it does not hold. Probed here with `dxil.dll` validating, on a buffer whose dword i holds 100 + i:

- **A structured handle whose declared stride differs from the view's:** the RTX 5070 addresses by the view's stride; the Radeon integrated GPU and WARP address by the declared stride. No single lowering is right on all three.
- **A raw handle over a structured SRV (what #193 does):** the Radeon and WARP read the byte asked for. The RTX 5070 reads byte B x 3 for a stride of 12 and B x 4 for a stride of 16 or an RGBA32F view, but byte B for a stride of 20. With #193's own 12-dword test buffer the wrong byte is past the end, which is the `0` the reviewers reported.

## Not verified, and what this does not fix

It also means the recorded stride on its own doesn't tell you the slot's view is structured.

Here is what that means for this PR, read at `1f3c184`:

- **The indexed unknown-stride path is safe on NVIDIA.** `runtime_view` takes its handle from the entry's raw slot. That slot is the host's own raw alias of the host copy (`Viewed::Bytes`), or the null raw alias (`Viewed::Unknown`). It is the title's slot only for `Viewed::Own`, which means a raw view or a non-buffer resource. `host_resource` is `Some` only for textures, so a structured or typed buffer view always gets an alias. A raw annotation never lands over a structured view here.
- **The follow-up (your item 3).** The unindexed forms still use `handle(.., (11 | u, 0))` over the title's slot: the `None =>` arms of the buffer load, store and atomic, and `s_buffer_load`. Sending them through `stride_entry` with `byte = off + bias` would make them correct whatever view kind the title made. Picking a structured annotation from the recorded stride would not, because of the black-frame case above.
- **Other slot writers.** Every path that writes a view into a host heap slot needs `note_view` or `forget_view`. Upstream that is only `make_at` and `mirror`, and both are covered. A stack that adds another writer without the call leaves the entry at 0, so the read goes to the slot itself (raw over structured, zeros on NVIDIA). Worse, it can leave an entry naming a previous buffer's alias, and then the read returns that buffer's bytes with no warning.
