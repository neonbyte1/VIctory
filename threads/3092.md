## Description

Split out of #2973, as asked in its review.

`WriteFile` only promises an atomic append for a single sector, and a crash record spans many. Under Wine, `crash::tests::concurrent_crash_records_stay_together` saw two records interleave: it writes from several threads of **one process**, which is the case this fixes.

Each record is now written in one append, under a process-local lock. The handler doesn't wait on it for long, because the exception may come from the thread that holds it. After about 10 ms it writes anyway: a rare interleaving is better than a lost report.

Two processes writing the same log aren't covered; the lock is process-local. I haven't seen that happen, and covering it would need a named mutex taken from inside an exception handler, which I'd rather not add without a case for it.

**Tested** (Linux, GE-Proton11-14 Wine, RTX 5090): `victory-loader` tests under `cargo xtask wine-test` (#1218), 39 passed, 0 failed. Not run on Windows.

The bounded `try_lock` + `yield_now` wait (`append_guard`) with poisoned-lock recovery and timeout fallback is a pragmatic way to serialize multi-thread crash appends without risking self-deadlock if an exception fires while holding the lock.

Two minor non-blocking suggestions:
- In `append_record`, acquiring `_guard` after `OpenOptions::new().create(true).append(true).open(file)?` (so the mutex only guards the `file.write(record.as_bytes())` call rather than handle open/close, which can take milliseconds under Windows AV minifilters) would shrink the critical section and make the 10 ms timeout much less likely to trip under burst contention—`FILE_APPEND_DATA` already seeks atomically per write across separate handles.
- Adding a small unit test that holds `APPENDING` on the current thread and verifies `append_record` still completes after the ~10 ms timeout would directly cover the re-entrancy fallback path.

LGTM.
