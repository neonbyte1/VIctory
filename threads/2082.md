## Description

## What

- **`docs/linux.md`** (53 lines): how testers run VIctory under Wine/Proton. It's marked unsupported.
  - **Setup:** vkd3d-proton's native `d3d12`/`d3d12core`, and Microsoft's `d3dcompiler_47.dll`.
  - **NVIDIA:** `VICTORY_PIPELINE_JOURNAL` from #491, and the passes that time out, linked to where they are tracked.
  - **The wineserver patch:** a link to ajsem1337's comment in #340, the Wine bug and the wine-cachyos PR.
- **`README.md`:** one line under Getting started linking to it.

## Why

**The compiler point** is the one that matters most and isn't written down anywhere else. Wine's builtin `d3dcompiler_47` refuses VIctory's run-time helper shaders. Then every indirect draw and dispatch is dropped (`no argument clamp: indirect execution dropped`), and most of the world is not drawn. This is likely behind several Linux reports of a blue, white or empty picture. With Microsoft's DLL, the world is drawn.

**The wineserver patch** is worth knowing about: a world frame goes from about 4 s to 1 s here (RTX 5080), and about 3 s to 1 s on an RX 9070 (measured by Beqren).

## Changed after review

The first version also carried the Wine patch ports (about 540 lines, LGPL) and scripts that fetch and build Wine (`tools/wine/`). Following the triage, those are out of the tree now. The doc links to [notes kept outside the repository](https://github.com/desplmfao/VIctory/blob/renderer/docs/linux-wineserver.md) instead.

### Comment by @Deilach — 2026-11-25T05:13:52Z

<https://github.com/Marvisak/VIctory/pull/2082#issuecomment-7153570759>

Tested a different path, on AMD: CachyOS, RX 9070 XT (RDNA4), RADV (Mesa 26.3.1), system Wine 11.22 rather than Proton, with vkd3d-proton master. Here's what AMD users will hit that the doc could cover:

1. **RADV crashes on entering the world with any released vkd3d-proton.** `dxil-spirv` makes invalid SPIR-V for some world shaders: a loop exit that isn't a structured exit, which `spirv-val` rejects. RADV then segfaults in `radv_shader_spirv_to_nir`, and the process ends with exit code 3 and no message. The fix is dxil-spirv's structurizer rewrite (`71967a38`, 2026-10-27). It's in vkd3d-proton master, but not yet in a release: the latest tag, v3.1 (2026-10-28), pins a dxil-spirv from 10-26. Building vkd3d-proton master fixed it here (`meson setup --cross-file build-win64.txt --buildtype release build64 && ninja -C build64`, then use its `d3d12.dll`/`d3d12core.dll`). Is the "vkd3d-proton 3.2.0" in the doc a proton-cachyos build? There's no v3.2 tag upstream.
2. **Wine's HLSL compiler can't build VIctory's two runtime shaders.** These are the indirect-argument clamp and the 16-bit depth conversion (#909, #170). Proton's `d3dcompiler_47` is Wine's too. Without them every indirect draw is dropped, and the world is mostly black. Until #1279 or #2093 lands: `winetricks d3dcompiler_47`, or `protontricks <appid> d3dcompiler_47`.
3. **vkd3d-proton refuses some things Windows drivers accept.** These have open fixes:
   - mesh pipelines that blend on integer render targets: #806, #2042
   - castable format lists, because vkd3d-proton has no `R10G10B10_XR_BIAS_A2_UNORM`: #2101
   - a discard inside a loop, which runs to the loop limit (0.4 s per draw): #2043

A DualSense under plain Wine needed winebus `DisableHidraw=1` and `Enable SDL=1` here.

Happy to send these as a follow-up PR to `docs/linux.md` after this one lands, if you'd prefer that to folding them in.

1. **Pin the exact Wine commit.** Take it from the Proton tag rather than the branch head. Today they are the same commit, but Experimental moves:
   ```sh
   gh api "repos/ValveSoftware/Proton/contents/wine?ref=experimental-11.0-20261112" --jq .sha
   # 5b557605b4e51f0853ec8e0e4f0eb536c669fae3; the installed tag is in "<Proton>/version"
   ```
2. **Check the built server against the Proton it will run with, not only print the version.** Valve's committed `include/wine/server_protocol.h` says 930 and lacks the fsync requests, so the server does not compile from it. `tools/make_requests` (run by `autogen.sh`) regenerates it as 931.   
   ```sh
   V=$(sed -n 's/^#define SERVER_PROTOCOL_VERSION //p' src/include/wine/server_protocol.h)
   objdump -d --no-show-raw-insn "<Proton>/files/lib/wine/x86_64-unix/ntdll.so" | grep -F -c "\$0x$(printf %x "$V"),"
   # 2 here (cmp $0x3a3 and the error message); 0 means the source is not the one this Proton was built from
   ```
   With a prepared source directory that already has a `configure`, `autogen.sh` is skipped, so the header there is worth checking.
3. **The server runs in umu's steamrt4 container as built.** I configured with nearly everything off, as the script does, plus `--disable-tests`, and left inotify on, as the stock server has it. Built that way, its dynamic imports match the stock server's: libc only, GLIBC_2.38 at most. A full copy of the Proton directory (`cp -a --reflink=auto`) with only `files/bin/wineserver` replaced also works as the "copy" step. Every file in it is real, so ntdll finds the new server.

### Comment by @slauko — 2026-11-25T14:04:15Z

<https://github.com/Marvisak/VIctory/pull/2082#issuecomment-7164711201>

Three things every tester on Linux will hit that `docs/linux.md` does not have yet — each with the log line that names it.

**1. The start screen waits for ever without a pad — it is a phantom pad.** Under Wine, XInput can report a gamepad that never presses a button: here the keyboard interface of a Logitech G502 (an HID interface with `BTN_GAMEPAD`, `/dev/input/js0`). The runtime gives the title its keyboard stand-in only while XInput has no pad at all (`any_pad` in `crates/victory-hle/src/modules/gameinput.rs`). The log tells them apart: `input device device=0 connected=true` is the phantom pad, `device=4` the stand-in. `SDL_GAMECONTROLLER_IGNORE_DEVICES_EXCEPT=0000/0000` keeps every pad from Wine's side, and Return goes through the start screen. (Zettrox/ztrx#2 documents this as a "known Wine gap".)

**2. Tools need a display too.** `victory warm` or `translate --pipelines` with `WAYLAND_DISPLAY` and `DISPLAY` both unset gets no Vulkan surface extension: `DxvkInstance::createInstance: Failed to create Vulkan instance`, then `no host D3D12 device`. `warm` still translates, but under a key made without the device's facts (wave size, view limit), and the run never finds those entries — the cache is warm and cold at once. Start tools on an Xvfb like the run. With `WAYLAND_DISPLAY` set and no X display, Wine opens on the tester's real desktop instead.

**3. Once the pipeline library works, the second launch hangs.** With VIctory#1722 in (the empty library with a null blob; vkd3d-proton refuses the dangling one) the library is saved — and the next launch starts every pipeline the last run drew with early: 1,657 here. The title presented no frame after frame 32 and its watchdog ended it (`0xc0000005` at `title+0x2215c35`, 45 s). The same binary without the library ran the title screen at 30 fps. `VICTORY_EARLY_PIPELINES=0` (fxceless/victory-fork#845) has pipelines requested on first use, which loads them from the library all the same.

Two smaller ones for the setup section:

- **vkd3d-proton from `ec20719` on NVIDIA.** Older builds still have dxil-spirv's legacy structurizer, and the driver crashes or hangs in the first world compute pipelines (fxceless/victory-fork#210). Proton Experimental of 2026-11-12 bundles `2576c0b4a`, 39 commits behind.
- **`VKD3D_SHADER_CACHE_PATH` is a folder.** Given the path of a file, vkd3d-proton logs `Failed to map read-only cache` and compiles every pipeline again on every run.

Measured with Proton Experimental `20261112`, vkd3d-proton `master@ec20719`, an RTX 3080 Ti, and the fork line (fxceless/victory-fork with uiliannn/VItoriaBr): menus 25–30 fps, the intro at 1.3–2.5 fps with a tree-indexed wineserver. The full list in the order it failed is in fxceless/victory-fork#6.
