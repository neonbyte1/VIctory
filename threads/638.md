## Description

*From a tester working with Claude (AI-assisted); measured on my own machine.*

These are diagnostics-only switches I used to chase the NVIDIA world hang (#71) and the black world. Release builds are unchanged.

## Switches

**`VICTORY_PRODUCERS=1`**
- When a draw or dispatch is dropped, it keeps what that work would have written: table UAVs resolved from the console shader's own used-resource list, plus render targets.
- When work that runs writes a range, the range is forgotten.
- It logs once per pair any running draw that reads one of those ranges: `reader=[mesh …] dropped=compute … what=buffer 0x…+0x…`.
- On an RTX 5090 it pointed at four compute producers that fail on `a lane-mask join of an untracked mask`, whose outputs mesh and compute passes read across the frame. Details in #71.

**`VICTORY_SHOW_TARGET=<n>|busiest`**
- Presents a render target instead of the title's picture: the frame's n-th written target, or the busiest 16:9 colour target.
- In the first mission's world, `busiest` shows the G-buffer: power lines, poles, a fence, signs and people in false colour. That shows the world is partly drawn under the black picture. The ground and buildings are missing because their mesh shaders don't translate.
- It logs each frame's target list at power-of-two frames.

**`VICTORY_CAPTURE_BUSY=<draws>[,<count>]`**
- Captures the frame after one that ran more than `<draws>` draws, and dumps its targets when `VICTORY_DUMP_TARGETS` is set.
- World frame numbers vary from run to run, and the world often hangs before a fixed `VICTORY_CAPTURE_FRAMES` number.

**`VICTORY_DUMP_FAILED=<dir>`**
- Writes every shader that doesn't translate to `<dir>/<stage>-<hash>.dxbc`, for `victory shader-info --disasm`.
- Runtime hashes otherwise can't be traced back to a container.

## Testing

- On `main`: `cargo build --profile diag -p victory --features diagnostics` and `--release` both build.
- `cargo test --release -p victory-gpu --features diagnostics`: 45 passed. Without the feature: 43 passed.
- Used in game on a branch with #233, #439 and #458 stacked.

Four of the title's fail-fast writes are NOPed in my copy (`mov dword [0]` sites; on 1.0.2.1 these are the 11-byte instructions at offsets 0x2215c35, 0x23cf683 and the bare `int3` at 0x247af2d — per-build offsets, and NOPing a write without its trailing `int3` just re-breaks at +11). `TdrDelay`/`TdrDdiDelay` raised to 60 for the real GPU.

**Result.** The run gets much further than before — 3,250 draws in a frame at 1 fps — and then:

```
reads what only dropped work writes reader=[compute 0fc1b11eb36efdb2] dropped=compute 149cb3508b989d0e what=texture 0x0 frame=1261
... (same shape for several reader/dropped pairs, frames 1,190-1,261)
```

Two things I ran into using `VICTORY_SHOW_TARGET` on NVIDIA under Proton (RTX 5080, vkd3d-proton 3.2), on #185 + `main` with this PR merged:

**1. A fixed index can crash vkd3d-proton.** `Host::present` resizes the swapchain to the shown texture's size and then `CopyResource`s it into the back buffer. With `VICTORY_SHOW_TARGET=3`, a loading frame's target 3 was a 2048×2048 texture with mips. The log shows `Reallocating swapchain (2048 x 2048)`, then:

```
Assertion failed: level_count == d3d12_resource_desc_get_active_level_count(&src_resource->desc), file ../src-vkd3d-proton/libs/vkd3d/command.c, line 11353
```

`CopyResource` needs identical resources, and the back buffer has one level. This was 2 of 2 runs, at the same point. Filtering the index to presentable textures stopped it:

```rust
Show::Index(n) => targets
    .get(n)
    .filter(|(_, c)| {
        // SAFETY: a live resource.
        let d = unsafe { c.texture.GetDesc() };
        d.MipLevels == 1 && d.DepthOrArraySize == 1
    })
    .map(|(_, c)| c.clone()),
```

`CopyTextureRegion` of subresource 0 would also work and would show mip 0 of such textures.

**2. The per-target count is binds, not draws.** `note_target` runs once per render-target bind or UAV use, so `(n draws)` in the frame list and the `busiest` choice count binds. In the world on this title the G-buffer layers (2560×1440 here) get only about 26–35 binds per frame, while the frame has about 4,000 draws. `busiest` then picks a target with many binds but little coverage; in the prison it showed a small cluster of what looks like hair in the middle of the screen. Counting draws per bound target in the draw path, or labelling the number as binds, would make the list easier to read.

**Update, tested `d6e50b8` under vkd3d-proton** (same machine and stack, with your `capture.rs` instead of my local filter): the reproducer, `VICTORY_SHOW_TARGET=3` with unattended input, now gets through loading into the prologue with no assertion and no 2048×2048 swapchain, and the frame list says `binds`. Thanks for the quick turnaround.

One side effect with a fixed index: in frames where target 3 isn't presentable, the title's own picture is shown instead, at a different size. The swapchain then gets reallocated back and forth, 18 times each between 2560×1440 (the target) and 3840×2160 (the title's picture) in the first minutes. That costs a reallocation each time and reads as flicker. Keeping the last presentable target in those frames, or scaling into a fixed-size back buffer, would avoid it.
