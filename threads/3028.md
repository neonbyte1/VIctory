## Description

On an RTX 5070 Ti (Windows 11, native D3D12), GTA VI in the world runs at 0.4–0.8 fps. With `VICTORY_GPU_TIMING=1 VICTORY_D3D12_DRED=1` (diagnostics build), the GPU takes 1.1–1.8 s per frame and the CPU 0.1–0.4 s. The GPU time is spread over ordinary draws. The wave64 compute programs (console flow, #439) are not where it goes.

Costliest commands, ms per frame (several 5 s windows):

| command | ms/frame | calls/frame |
|---|---|---|
| draw `[vertex 58d926085fca4999, pixel edc1cad8ffb79bc9]` | 45–123 | 2–4 |
| indirect `[mesh b7a81f5b96f4ca93, pixel 43e24028d4a1faef]` | 72–96 | 30–157 |
| indirect `[vertex 4e35b816f2f91d68, pixel 659fe9cae59dbd88]` | 19–122 | 9–27 |
| draw `[vertex 1ce8ba2fe12072c1, pixel 4dd4a3d69c1bd8ca]` | ~61 | 1 |
| draw `[vertex c5310733d58458c8, pixel 5460ce5f3b925eee]` | 20–59 | 7 |
| dispatch `[compute a7eeed0646be1ab7]` | ~48 | 1 |

Moving host copies into GPU upload heaps does not change these numbers. That covers buffers (#2870) and, in a local change, the loose windows as well, in the spirit of #2875: 5.2 GB of copies sat in video memory against 1.3 GB before, and the per-draw times stayed the same. So these draws are not bound by shaders reading the copies across PCIe. A single draw at ~61 ms points at the translated shaders themselves, or at what they index: the paged view heap (#2121), descriptor reads, or texture paths.

I can run more diagnostics builds or dump specific shaders if someone has a lead.

| PR | What moves to video memory | Default | Reported (card) |

| #2993 | copies of title buffers, admitted under a quarter of the DXGI budget (`=1` vertex/index/constant, `=2` written heaps) | off (`VICTORY_VRAM_COPIES`) | frame mean 910 → 817 ms; GPU / preparing / copy-back 316 / 295 / 121 → 216 / 268 / 130 ms (RTX 5070) |
| #2705 | a DEFAULT-heap side for copies of title buffers | off (`VICTORY_CARD_COPIES`) | frame 578 → 565 ms, GPU 270 → 222 ms, while drawing 2,749 vs 2,081 draws |

| #2734 | hot title buffers used in place, 60 % of the budget | off; stacked on #2112, conflicts with `main` | — |
| #2875 | loose windows into GPU upload heaps | off (`VICTORY_LOOSE_IN_GPU_UPLOAD`) | non-local segment 104 % (pinned) → 55 % |
| #3228 | upload buffers into GPU upload heaps, indirect arguments into DEFAULT | follows `GPUUploadHeapSupported` | commit −291 MB, RSS −1.1 GiB |

**Overlap.** I merged each one locally onto #3312 (`576188a1`). #2993, #2705, #2734, #3102, #2875 and #3228 all conflict with it (`shadow.rs`, and `host.rs` or `memory.rs`). So does #3318, the quadratic-snapshot fix. #3470 and #3440 merge cleanly. Whichever of these lands first, the others need rework.

**Two observations from the numbers above:**
1. Where a PR reports both, GPU time falls a lot but the frame stays bound by the CPU: #2993's preparing time is still 268 ms, and #2705's frame moves 13 ms on 48 ms less GPU. After the copies move, per-frame CPU preparation is most of what is left.
2. The no-gain reports used GPU upload heaps: this issue's local change put 5.2 GB in video memory with unchanged per-draw times, and #3102 showed none on the RX 7900 XTX. The large GPU gains (#3312, #2705, and #2130 via #2993) are from DEFAULT-heap copies. That is a correlation in five reports, not a measured cause.

**From a fork, for the sizing:** trustno1-coder/VIctory-NVIDIA has commit `22035389` (readmet3xt-lab). It changes a 512 MB cap on card copies of title buffers to 18 % of the budget (512 to 2048 MB), plus 9 % (at most 1024 MB) for windows. On an RTX 4070 SUPER it reports the opening's six heaviest compute passes going from 20-42 ms each to 0.2-0.4 ms, and gameplay from 3 to 21-25 fps. #3505's 8 GB laptop result (`VICTORY_MEMORY_CARD_MB` 1024 → 2048, about 6×, from another fork) points the same way. The forks' code is GPL-3.0 like this repo.

My RTX 3070 8 GB test run of #3312 is in #3312: no regressions against `main`, and its VRAM path is used on an 8 GB card.
