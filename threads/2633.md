# Marvisak/VIctory#2633: Shaders: wave64 compute programs run in 32-lane halves on hosts of 32-lane waves

- PR by @chippy01, opened 2026-11-25T17:15:20Z, state **open**
- <https://github.com/Marvisak/VIctory/pull/2633>
- Archived copy; the original thread is authoritative while it exists.

## Description

## The problem

A console wave64 compute program that needs the console's lanes (cross-lane reads, masks read as numbers, LDS one wave shares) declares `WaveSize(64)`. NVIDIA and Intel run waves of at most 32 lanes (`WaveLaneCountMax` 32) and refuse it. On an RTX 3070 Ti the debug layer says:

> Shader wants wave lane count of 64 but maximum wave lane count for device is 32 (id 622)

and the pipeline is refused with `E_INVALIDARG`. A Series S run to the loading screen refused 100 compute pipelines; 95 of them were for this reason.

## The change

On such a host, a wave64 program that needs the console's lanes is translated for waves of 32 ("halves", `emit::lower::halves`, set by `emit::Options::host_wave32`). The thread relabelling gives each host wave a 32-aligned run of thread ids, so host wave `2w + h` holds lanes `32h..32h + 31` of console wave `w`. What each cross-lane operation needs, and where the halves can meet, is in `docs/wave64-on-32-lane-hosts.md`.

**Level 1, exact within a half** (the first commits): DPP rows, `ds_swizzle`, and `ds_bpermute_b32`, which the console's wave64 permutes within each half on its own (RDNA2 ISA; measured on RDNA2 in #573). A lane's bit of a mask held as a number, `v_writelane_b32`, `v_mbcnt` and the row a DPP row mask names take the **console** lane. A first-lane read of a value proven the same in every lane of the console wave (`halves::lane_uniform`) is the host's. A group of 32 threads or fewer is one host wave, which holds its whole console wave.

**Level 2, the halves trade where every thread meets** (`Lower::trade`): each half writes its words to group-shared slots, a group barrier, each half reads both, a second barrier. Only at blocks every thread of the group reaches the same number of times (no lane-dependent branch has them in its region; in groups of several console waves, no branch at all), since a barrier one half skips hangs NVIDIA. Where the program's LDS takes the host's whole 32 KiB and leaves the slots no room, they are its first dwords, borrowed: saved before the trade and given back after, three barriers more for such programs only.
- `v_readlane_b32`: the half holding the lane gives it.
- `v_readfirstlane_b32`: each half's first lane in EXEC and whether it has one; the low half's if any.
- Lane masks read as data: each half's ballot is one dword of the console's mask.
- Whole-wave reductions and prefix sums: each half's part, combined low half first.
- LDS of a group of one console wave (33-64 threads, which the console compiler leaves without barriers): group barriers put the two host waves in the console's order, before an access that may meet an earlier one and around regions only some lanes run.

**Level 3, inside a branch or a loop only some lanes run** (the per-lane form turns the console's wave-wide tests, `s_cbranch_execz` and `s_cbranch_vccz` on a ballot, into such branches and loops):
- **One half alone** (`emit::lower::confine`): where a block's entry condition shows that only one half's lanes can run it (`tid < 16` in an LDS tree step), that half's host wave runs it alone, in the console's order, and nothing crosses.
- **Wave-wide** (`emit::lower::wide`): otherwise the region runs wave-wide (the blocks not every thread meets at, entered from one block and left to one or reaching the program's end): every thread runs every block of it, each block acting only in its own lanes (guards take the block's lanes in, join phis pick per lane by the edge it came by), so the halves trade and order LDS there. A branch the whole group takes together (a scalar compare in a group of one console wave, as the title's programs open with to skip their work) may also go around the region to its join, or into it past its head: the group then runs the region from its first block with every lane in the block it went to and none before, and a descriptor chosen by control flow where it goes in is the console wave's scalar, folded as below.
- **Wave-wide loops**: a loop each lane leaves in its own round (the console's scalarization loops) runs as the console's wave runs it: every thread goes round while any lane of the group does, decided across every half of the group at the end of each round. A lane that leaves is out of the loop from then on, and what it holds (VGPRs by their guarded writes, compare bits kept per lane) stays as it left it.
- **Scalars are the console wave's.** On the console a scalar belongs to the wave: after a branch or a loop only some lanes take, every lane holds what the last block the wave ran left, also a lane that skipped it or never entered the loop. In a wave-wide region a scalar phi takes the value of the last of its edges' blocks that some lane of the wave ran (each half's ballot of the block's lanes, traded), and a loop keeps a scalar read outside its block in every lane from the last round the wave ran that block (`Lower::wide_fold`, `wide_keep_block`). A join that reads a scalar whose value differs by the way a lane came, outside such a region, runs its region wave-wide on the next attempt (`Lower::scalar_join`).
- Only where an attempt was refused for want of a meeting, or a join reads such a scalar: programs that need neither are lowered exactly as before, and should the attempt for a scalar fail, the one before it stands. Regions with scalar side effects or loops entered past their header are not taken.

**First lanes alone bring a program into halves.** A wave64 program whose only cross-lane read is the first lane of a value `halves::lane_uniform` does not prove alike in every lane now runs in halves too (`halves::first_across`); before, each 32-lane host wave read its own first lane (lane 32's in the upper half). Should every attempt in halves fail, it is lowered as before, each host wave reading its own first lane, which is exact for the compiler's scalarization loops and for values it keeps the same in every lane (one title program, a scalarization loop).

**Sections the simulation cannot follow run step by step** (`halves::Literal`): a whole-wave reduction the console compiler expands can leave a value whose lanes hold different things (each half's sum in some lanes, the wave's in others), which a later masked write keeps in the lanes it leaves out. Main keeps such a value as zero there; in halves, where every thread meets and the group is whole console waves, the section now runs instruction by instruction (DPP and the lane permutes within a half, its lane reads across the halves traded), so those lanes hold the console's values. In a block run wave-wide the steps run in every lane of the console wave and the section's lanes are the block's (a reduction there counted lanes that had left the loop), and a section where not every thread meets runs its region wave-wide. 16-bit sums run the same way, each step rounded as the console's. `v_permlane16_b32` and `v_permlanex16_b32` are lowered per instruction in compute on every host (before, only inside sections).

**Still refused**, each with a reason naming the host: a cross-half read in a region of neither shape (1), groups of several rows a host may tile (rows 32+ threads wide or not a power of two; measured here and in #2126; 6).

**Two fixes to this PR's own earlier commits**, found by the random tests: a loop's latch (and a loop of one block) counted as a point where every thread meets, so a trade there put barriers in a loop the two halves may go round different numbers of times, which hangs NVIDIA; and a value written in such a loop counted as the same in every lane after it, though each lane holds its own last round's (a first-lane read after the loop gave the upper half lane 32's value). No program of the title changed outcome.

`victory-gpu` asks the device once (`D3D12_OPTIONS1`) and translates for it. **The shader cache keys on it**, so entries made for 64-lane hosts are never read on a 32-lane one, or the other way round. `victory translate --wave32` translates for such a host offline; with `--pipelines` it follows the GPU that makes them.

New code lives in `emit/lower/halves.rs`, `confine.rs` and `wide.rs`, with a few named hooks in `lower.rs`; `lower.rs`'s unit tests move to `lower/tests.rs` (as #233 does), so `lower.rs` is 480,649 bytes, under the policy's 512 KiB cap.

## Tests

`emit::halves_tests` runs hand-encoded programs on **every hardware adapter**, in halves everywhere and as one wave64 where the adapter has 64-lane waves, against the console's results: an RTX 3070 Ti (halves) and the Radeon iGPU of a Ryzen 9 7900X (RDNA2, halves and wave64), 0 lanes differ.
- Level 1: DPP, swizzles, permutes, `v_mbcnt`, `v_writelane`, constant masks, DPP row masks, first lanes kept, every thread's id in 4x4x4 to 64x1x4 groups (and tiled shapes refused).
- Level 2: lane reads, first lanes (also under a narrowed EXEC), masks, sums and prefix sums in groups of 48, 64, 96 and 128; one-wave LDS across the halves, across a branch, and after a spin that only barriers keep in order (64 of 64 lanes wrong without them, on both GPUs).
- Level 3: LDS tree steps in either half alone; branches of both halves run wave-wide with first lanes, masks, lane reads (including a lane outside the branch, which keeps its old value as on the console) and one-wave LDS written and read or written twice; each trade costs two barriers, a one-half region none. Loops each lane leaves in its own round (the halves going round 3 and 4 times), with first lanes, masks and LDS read across rounds, in groups of 48 to 128; a first-lane read after such a loop; lanes that end partway, then a mask and a first lane over those left.
- Whole-group branches: lanes that end, a mask and a first lane, with a scalar branch taking the whole group around all of it or into the first-lane read with every lane, also with the stores' descriptor chosen where the group goes in, in groups of 48, 64 and 128 (the modules validate).
- Sections step by step: the console compiler's wave64 sum whose lanes 32-63 hold twice the high half's, kept by lanes a later masked write leaves out, in groups of 64 and 128 (main's one-wave64 form stores 0 in 44 of 64 lanes there); a 16-bit wave sum. Both lane permutes with every lane and with half the lanes, plain, `bound_ctrl` and `fi`, in groups of 48, 64 and 128.
- Scalars: a first-lane read in a branch of each of Lyrnc's masks (one half, the other, both, alternate, one lane in either half, lanes 31 and 32, none), stored inside the branch and by every lane after the join, in groups of 64 and 128, the program in halves for that read alone; a loop console lane t runs t rounds of (lane 0 none), reading lane 40 and counting rounds in scalars every lane stores after it, with an ordinary latch and with the read in a branch whose EXEC is joined again before the way back, in groups of 48, 64 and 128 (after pickles976's consumers of #439's `lane_read_loop_tests`); the console's wave64 sum run step by step in a wave-wide branch.
- A trade beside LDS of the host's whole 32 KiB, through slots borrowed from it: every thread's LDS dword is the program's again after it (groups of 48, 64 and 128, the last in halves for its first-lane read alone).
- Refusals name their reasons; a kept refused value refuses the write instead of storing 0; the hand-encoded words are checked against the disassembler.

`emit::halves_random_tests` generates random wave64 programs (cross-lane steps at the top level, in branches one inside another and in loops each lane leaves in its own round, LDS, scalar branches, lanes that end partway, whole-group branches around or into a lane branch) and runs each in halves on both GPUs and as one wave64 on the Radeon, lane by lane: 3,000 seeds, 2,999 compared, none refused in halves, 0 differ (seed 1922, which crashes the Radeon driver's compiler making the one-wave64 reference, is skipped). It found the kept-value bug and the two loop bugs above, each fixed in its own commit, a Radeon compiler fault after a loop with a second way out, which the loops avoid, and two places where a region that could run wave-wide was not asked for.

Checks: `cargo clippy --workspace --all-targets --locked -- -D warnings` and the same with `--all-features`: clean. `cargo xtask policy`: ok. `cargo test -p victory-shader --lib -- --test-threads=1`: 332 passed, 3 failed, the **same 3** as on `main` on this NVIDIA machine (`stride_tests::a_heap_buffer_read_by_element_takes_the_views_stride`, `stride_tests::a_heap_buffer_read_where_no_buffer_view_is_reads_zeros`, `synthetic_tests::gathers_at_a_level_match_the_hardware`); `memory_tests::heap_direct_texture_reads_mark_their_heap_index` crashes the test process on `main` here too and is skipped.

## Related pull requests

This overlaps #189, #192, #233/#320/#439, #1890, #2176, #2214, #2711 and #2925 (wave64 on 32-lane hosts) and #578 (refusing them). It differs in that cross-half reads are refused or traded at the site that makes them, with a reason (programs whose crossing value is unused still translate), the halves meet only where every thread provably does (wave-wide only where needed, instead of the console flow everywhere), and every form is checked against the console's own wave64 on an RDNA2 adapter in the same test. The cache-key idea is #2176's (n-romanovich). It does not change `ds_bpermute_b32` for 64-lane hosts, which is #573's.
