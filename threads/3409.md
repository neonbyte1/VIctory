## Why a smaller tested set, not everything that is green

In #3327 I merged every open PR that merged cleanly and had a green `check`, 375 of them. That set builds and passes `cargo test`, but **it does not run the title**. Each problem below was found by bisecting that set or by others' reports:

- **Device removal (`0x887A0004`) about 70-90 s in**, at the first cutscene, on a machine with three adapters. One cause found in the set was #967 (the adapter choice); other combinations still did it after #967 was reverted.
- **Access violations, writes to read-only pages**, in a group of `xmem` / guard PRs. #2848's guard-reopen commit was one of them, confirmed independently in #2848 by @Jackster and since removed from it.
- **A black or washed-out picture with the audio still running.**
- **Tests that pass alone but fail in the set:** #2012 (the table decoder fails about 320 shader tests together with the rest), #2336, #2731, and #2626 (with a PR of mine that changed the same formats, since closed in favour of #2626).
- **A semantic conflict** (#2706 with #1653) and `lower.rs` growing past the 512 KiB asset policy once enough shader PRs are combined.

So "mergeable and green" alone is not enough: individually fine PRs break the title in combination. This branch therefore grows only by steps that keep the title running.

## How each PR got in

PRs taken, most useful first:
- triage verdict `merge-candidate` on their current head;
- the change is in runtime code, not only tests;
- no negative reports from testers in the discussion;
- ranked by the number of independent confirmations and by whether the title fixes a crash or wrong behaviour.

They were added in batches (six at first; later rounds larger, halved on failure). Since the device-removal fix, every new state also gets **three** title runs, with the D3D12 debug layer on. A batch stays only if all of these hold:

1. `cargo check --workspace --all-targets --locked`
2. `cargo test --workspace --locked`: 0 failures (the one known flaky `relaunch_closes_its_duplicated_process_handle` is ignored)
3. **The title for 300 s** (release + `diagnostics`, Series X, a scripted `Enter` / hold schedule through #3392, warm shader cache), judged automatically, with screenshots every 30 s also looked at:
   - no `device removed`;
   - no unhandled exception or panic;
   - no black picture from 150 s on;
   - the world reached (over 10 000 draws a frame).

A batch that fails is halved until the PR that fails it is out. That PR is listed with the reason.

The base, `main` + #3392 alone, reaches the prison yard in 300 s with 10 552 draws a frame. #3392 is in the base only because the scripted input needs a held key.

## A fix on top: #3540 (an invalid raw SRV removed the device)

After the batches from #2472 to #1701, the title removed the device in 3 of 4 runs, about 200 s in. #2472 + #3035 had also needed a second run. Each time it was `DXGI_ERROR_INVALID_CALL`. With `VICTORY_D3D12_DEBUG=1` the debug layer named the call: `CreateShaderResourceView` of a **raw** view with `FirstElement (2)`. The host wants raw views to start on 16 bytes; the console takes any dword.

This is in `main` (`buffer_srv`), not in any of the PRs here. The PRs only change which host copies exist, so the faulting view came up more often. #3540 makes raw views (SRV, UAV and constant buffers) take a copy that starts on 16 bytes. It is merged here as its own commit.

With it, the same set: **3 of 3 title runs with no device removal** and no raw-view message from the debug layer; `cargo test --workspace` 930 passed, 0 failed; `clippy -D warnings` clean, also with `--all-features`.
