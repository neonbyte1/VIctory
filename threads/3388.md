# Marvisak/VIctory#3388: GPU: target dumps refuse a footprint the host could not give

## Description

### What is wrong
A diagnostics run with `VICTORY_DUMP_TARGETS=1` / `VICTORY_DUMP_WRITERS` aborted GTA VI (RTX 5090, Wine + vkd3d-proton) with `memory allocation of 103079215080 bytes failed`, right after `vkd3d_get_format: Invalid format -1`. It happened while dumping the fourth target written by one compute pass.

`dump_one`/`read_back` trusted whatever `GetCopyableFootprints` left in the footprint. For a subresource it can't describe, vkd3d-proton fills the layout with `0xFF` bytes (`memset(layouts, 0xff, …)`, `total = ~0`), so the footprint reads `Format = Width = Height = Depth = RowPitch = 0xFFFFFFFF`. Then:
- `f.Width * f.Height` wraps to 1 in `u32`, so the dump takes the "tiny target" path;
- that path builds a `Vec<String>` whose size hint is `f.Height`: 24 bytes × `0xFFFFFFFF` = 103,079,215,080 bytes, the failed allocation;
- the same footprint format goes to `CopyTextureRegion`, which is the `Invalid format -1` line.

`capture.rs` is the same on `main`, so any capture of such a target aborts there too.

### What changes
- `footprint_fits(desc, footprint)` (pure): the footprint's format has a known element size, its extent equals the resource's block-aligned mip-0 extent, the depth matches, the texel count is under a cap, and the row pitch holds a row. All with checked arithmetic.
- `read_back` also asks for the row count and row size, recomputes the bytes it needs, and refuses a short or implausible total (over 1 GiB) before it sizes any buffer.
- `dump_one` checks again before mapping, tests "tiny" in `u64`, and `to_rgba` refuses extents over 128 Mi texels.
- Each refusal logs one line with the resource, format, extent, pitch and total, and the dump continues with the next target.
- Typeless formats now decode as their typed twin with the same bytes (`R32_TYPELESS` → `R32_FLOAT`, `R24G8_TYPELESS` → `D24_UNORM_S8`, `R16_TYPELESS` → `R16_FLOAT`, BGRA typeless → sRGB), and planar depth uses the plane footprint's own format. `R32G32B32_FLOAT` is added.

#601 also touches `dump_one` (one line, slice bounds for mips) but fixes a different bug; whichever lands second needs a trivial rebase.

### Tested
- 3 new device-free unit tests for `footprint_fits` (including the all-`0xFF` footprint), plus the existing `capture::tests` (8/8) and `r32_tests` (6/6), under Wine.
- clippy `-D warnings` for `x86_64-pc-windows-msvc`, default and `--all-features`; formatting clean.
- In game: the same capture with this fix applied to my test build is running now; I'll add the result here.

**2. The mapped slice in `dump_one`.** It is now sized to the read-back
buffer's own bytes, `buffer.GetDesc().Width` (bounded by `MAX_READBACK`), and
the span within it is `row_bytes(pitch, rows, last_row)` — a new pure function
(`pitch * (rows - 1) + row`, every row pitched but the last). Everything that
reads the mapping stays inside it: `to_rgba`'s widest index is the last row's
own size, and the "tiny target" window uses the same row size instead of
`width * texel`. Block-compressed footprints are refused as undecoded (as
before — `to_rgba` never decoded them, and their height is texels, not rows of
blocks), so a BC height no longer sizes a slice.

The new test `tests::a_mapping_spans_its_rows_and_not_its_pitch` pins the
numbers from your matrix: 1×1 `R8G8B8A8_UNORM` → 4 (not 256), `D24_UNORM_S8_UINT`
64×64 → 32,512 (not 32,768), `BC7_UNORM` 64×64 → 4,096 (not 16,384), plus
2560×1440 `R8_UNORM` and the empty cases (no rows, no row, row > pitch).

On #601: this stays minimal and complementary — the only change to `dump_one`
is the length of the mapped slice and the row window inside it; nothing else
in that function moves, so the two changes should not conflict textually or
semantically (both bound the same slice).

**3. `read_back` / `footprint_fits`.** `read_back` now refuses a footprint that
names no rows, or no bytes in a row, by name (the same `row_bytes`, so
`rows.saturating_sub(1)` no longer carries the check), and `footprint_fits`
requires `d.SampleDesc.Count == 1`, so a caller that did not pre-filter
multi-sampled resources is safe too. Both cases are in the tests: the
multi-sampled description is refused in
`tests::footprints_of_failed_copies_are_refused`, and the zero-row/zero-row-size/
row-longer-than-pitch cases in `tests::a_mapping_spans_its_rows_and_not_its_pitch`.
