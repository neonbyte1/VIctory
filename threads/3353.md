# Marvisak/VIctory#3353: GPU: a frame whose presented image a dropped draw left unwritten is not shown

- PR by @neonbyte1, opened 2026-11-26T19:53:57Z, state **open**
- <https://github.com/Marvisak/VIctory/pull/3353>
- Archived copy; the original thread is authoritative while it exists.

## Description

### What is wrong
A draw whose pipeline is still being made is dropped once the frame's wait budget is spent, and leaves its render targets as they were. When that draw is the one that writes a presented image, the image still holds what was drawn into it the last time. Titles present two back buffers in turn, so the window alternates between two old frames.

In Grand Theft Auto VI's world start with a cold driver cache (seven runs, RTX 5090, Wine + vkd3d-proton), the first world frame first-binds ~1,900 pipelines. The final upscale (`VS_TAA2_SpatialUpscale` + `PS_TAA2_SpatialUpscaleWithDithering`) is one of them, queued behind the others: in one run it waited 41 s and then took 3.3 ms to make. Until then every other frame was black (the fade's last frame in one back buffer) and the others dim (the first fade-in frame in the other), 46 frames in a row. In every run the flicker stopped within one frame of that pipeline being made; runs whose cache was warm had it before the world started and never flickered.

### What changes
- A draw (or indirect draw / mesh dispatch) dropped because its pipeline is being made, whose render target is an image the title has presented, puts that pipeline at the head of the workers' queue, once (`make::hurry`).
- The next present of an image such a draw left unwritten is not shown; the window keeps the last frame it showed (`crate::shown`). The log says where a run of held frames starts and ends.
- A run of held frames lasts at most 10 s (`HOLD_LIMIT`): the pipeline held for is the next one a worker takes, and the longest worker job in my cold-cache runs was 10.5 s (typically 4–6 s). Past it the frames are shown as they come and the log names the pipelines waited for, so a pipeline that never arrives (a dead worker, a hung driver compile) cannot freeze the window.
- Pipelines that are refused or do not translate never count.
- `VICTORY_SHOW_UNWRITTEN=1` shows those frames as before.
- Diagnostics builds: the black-frame detector only sees frames that are shown, so held frames produce no black-frame warning; zero warnings is expected, not by itself proof.

Trade-off: a first-use draw into the back buffer (a new HUD element) whose pipeline misses the budget now holds the frame until it is made, which is the next thing a worker makes, instead of showing a frame without it.

Related: #2582/#2435 give full-screen passes their own workers (that would also shorten this if the upscale classifies as one, but never holds), #3025 orders graphics before compute; both edit the same queue in `pipeline/make.rs`, so whichever lands second needs a small rebase. I found no open PR that holds the present of an unwritten image.

### Tested
- New tests: `shown::tests` (an unwritten image is held once, an image never presented is never held, old images are forgotten, a hold is given up after the limit with an injected clock) and `pipeline::make::tests::a_pipeline_a_presented_image_waits_for_goes_first` (order, once, not when taken or made). They pass under Wine.
- clippy `-D warnings` for `x86_64-pc-windows-msvc`, with and without `--all-features`: clean; `cargo xtask policy` ok.
- In game: two 8-minute runs of the same build with the driver's and vkd3d-proton's shader caches off (`__GL_SHADER_DISK_CACHE=0 VKD3D_SHADER_CACHE_PATH=0`), so the first world frame starts with the backlog every time:

  | | without this change | with it |
  |---|---|---|
  | pipelines being made at the peak | 2,474 | 2,474 |
  | black frames presented after a non-black one | 52 (every other frame, 1280–1382) | 3 (frame 1 and two scene cuts, as in warm runs) |
  | `made first` | — | 1 (`vertex 0309a446…, pixel 4f4ec7b1…`) |
  | frames held | — | 1 (frame 1269, shown again at 1270) |
  | hold given up, Xid, device removed | — | 0 |

  Captures of frames 1300–1303 show the alternation without the change (dark, stale grey, dark, stale grey) and a steady image with it.

**Not fixed here:** after the upscale exists, the world stays dark (brightness 0–1) until a `CS_RaytracingResolve` compute pipeline is made, about 50 s and ~55 frames later in the cold run. That image *is* written, so holding is not the right tool; making the pipelines that feed the presented image earlier is a follow-up I'm looking at.

I resolved the `pipeline/make.rs` conflict between this head and #3025 in [`4a59f2e`](https://github.com/andrewpozdnakov7-jpg/VIctory/commit/4a59f2e12f3720f98f561e6013b72f2c31105b33), retaining both exact heads. A draw that holds presentation goes to the front of the graphics queue. Compute entries still take a compute slot, and a promoted entry already claimed by another worker does not take a second slot.
