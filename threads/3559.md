# Marvisak/VIctory#3559: -Res 1440 (native 1440p, temporal scale 1.0) breaks face and hair rendering; -Res 1080to1440 (0.75) is correct

## Description

Summary With -Res 1440 the prologue cutscene renders only Lucia's hair, eyes and teeth — the rest of the face is missing — and her hair shows a solid block. With -Res 1080to1440 the same scene is correct. DLSS is not involved: the 1080p path is correct with DLSS both off and on.

Environment

Windows 10 Pro 22H2 19045.4894, in-box d3d12.dll 10.0.19041.4355 + D3D12 Agility SDK 1.620.2 (required on Win10, see #753)
NVIDIA RTX 4070 12 GB, driver 610.62, HAGS on
i5-13490F (6P+4E/16T), 32 GB RAM
Title: Xbox Series build 1.0.2.1, blake3 b99f876b74d4a77f03af5f878223b27bd647b5c35a79d5decd9f716504239e93
Tree: this repo at f890cb5, plus the Agility SDK exports, cargo build --release --locked -p victory
Repro victory run <dump>\game_scarlett_master.exe --console series-x --execute with VICTORY_NATIVE_1440P=1 (what -Res 1440 sets), or with the launcher: scripts\play-VIctory_sm86.ps1 -Exe <exe> -Res 1440 -Dlss off. Watch the first cutscene where Lucia appears (about 2–3 minutes in).

Expected / actual Expected a complete face. Actual: hair, eyes and teeth only, plus a solid block on the hair. Gameplay is unaffected.

What is already ruled out

The five shaders 5ad3a82b1c3cc63a, 15c34c906ac8b908, 4273011b11446435, and mesh 4f23fd8d99482703 + pixel 2fd01fca16993001 / 6b6db9f1a526daeb all translate and bind in both configurations (first bind at frame ~23452 with 1440p, ~5701 with 1080p). No dropped draws, one translation failure total (compute 6b82bc7d22016cb5, unrelated wave32 case).
DLSS off vs on changes nothing; -Res 1080to1440 is correct in both.
What correlates apps/victory/src/native_1440p.rs:60-63 writes TEMPORAL_SCALE = render_width / 2560: 1.0 for -Res 1440, 0.75 for -Res 1080to1440. The broken case is exactly scale = 1.0, where the title's own temporal pass is effectively bypassed. -Res 1080to1440 additionally can run through the FidelityFX/upscaler path (prepare_upscaler, renderer 7), which is also correct.

Workaround Use -Res 1080to1440 (also about 2x faster here: ~18–21 fps vs ~10 fps at 1440p). The default -Res in play-VIctory_sm86.ps1 has been changed to 1080to1440 locally.

Note: analysis and report prepared with DeepSeek (AI-assisted); the observations and logs were produced by me on my own machine. No game files are included.

A data point from a tree without this switch, to help narrow it down.

**Where the switch lives:** `f890cb5` is a commit of [whiteh4cker-tr/VIctory_sm86](https://github.com/whiteh4cker-tr/VIctory_sm86/commit/f890cb55), not of this repository. `VICTORY_NATIVE_1440P` and `apps/victory/src/native_1440p.rs` don't exist on `main` (`63bcca4`); the same switch name also appears in fxceless/victory-fork (`play.rs`, `run.rs`). So the `TEMPORAL_SCALE = render_width / 2560` write described above is fork code, and the fork is probably the better place for this report.

**What `main` does here:** our test stack is `main` plus unmerged PRs for NVIDIA under Wine (listed in #3425), Series X profile, where the title renders at 2560×1440 on its own and no temporal-scale value is written by the host. RTX 5090, Linux, Wine + vkd3d-proton. In the prologue close-up of Lucia (frame 1500 counted from the first presented frame), the face is complete: skin, eyes, brows, lips and hair, no solid block. That matches the report's 1080-to-1440 case, not the broken one.

So the broken case seems specific to the fork's native-1440p path (scale 1.0) rather than to rendering at 1440p as such. I haven't run that fork, so I can't confirm the bypassed temporal pass as the cause.
