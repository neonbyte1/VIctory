## What

Console wave64 compute programs that depend on the lane layout run on hosts without 64-lane waves (NVIDIA: D3D12 range 32..32), as two 32-lane waves per console wave. Two forms, picked per program:

- **In-half split.** A program whose cross-lane reads are only DPP and `ds_swizzle` (reads within 16, 8, 32 or 4 lanes), with no mask read whole, no LDS and no whole-wave sections, declares `WaveSize(32)`. It uses the existing thread relabelling, and DPP row masks name the console's rows.
- **Console flow**, for groups of at most 64 threads (one console wave) without LDS. Every lane runs every block, as on the console:
  - `structure::structure_console` builds the per-lane booleans without resolving mask joins from what arriving lanes know (every lane arrives), and `Structured::execs` gives the lane's EXEC bit at each vector instruction.
  - The lowering guards every vector instruction with EXEC (`v_readlane`, `v_writelane` and `v_readfirstlane` ignore it, as on the console).
  - Branches are the console's `s_cbranch_*`: EXEC, VCC and mask-operation SCC tests are taken for the whole console wave, from both halves' ballots.
  - Each half's dword is exchanged through two group-shared slots between two group barriers. Since both halves take every branch alike, every thread of the group reaches each barrier, inside divergent branches and loops too.
  - Masks read whole (`s_bcnt1`, `s_ff1`, scalar compares) are the exchanged ballots. `v_readlane` and `v_readfirstlane` read the owning half; `v_writelane`, `v_mbcnt` and mask bit tests use the console lane.

  `lower` tries the per-lane form first. A program that needs the console flow stops with `CONSOLE_FLOW` and is lowered again from the console structure.

Also: `emit::host::Host::on(name)`, `adapters()` and `VICTORY_ADAPTER` for tests, so a machine with two GPUs can run each test natively (64-lane adapter, the reference) and split (32-lane adapter). `docs/architecture.md` summarizes the design (the longer `docs/wave64-on-wave32.md` was removed in `691ff20`).

Nothing changes on hosts that run 64-lane waves.

### How this relates to other open PRs

- **#189** (alfycs) also runs wave64 compute as two 32-lane waves with group-shared exchanges, and covers much this PR does not: groups of several console waves, LDS, whole-wave reductions and prefix sums, SGPR spills at constant lanes, and an emulation mode for WARP. It keeps the per-lane control flow and refuses exchanges outside blocks the whole group reaches. This PR's console flow covers exactly those refused cases: exchanges inside branches one half skips, and lane reads in loops the halves leave at different iterations (tests below). The two could be combined: the console flow for divergent single-wave programs, #189 for the rest.
- **#192** (kxiserino) gives DPP/`ds_swizzle`-only programs `WaveSize(32)`, like the in-half split here (and on 64-lane hosts too), and orders single-wave LDS with barriers, which this PR does not do. It has no cross-half exchange. Its DPP row-mask handling caught a bug in an earlier version of this branch, fixed in `727e884`.
- **#54** (alessiodeia) declares `WaveSize(32)` for groups of at most 32 threads and resolves SGPR spills in SSA. Groups of 33 to 64 threads, which this PR handles, stay `WaveSize(64)` there.
- **#94** adds `VICTORY_ADAPTER` with the same meaning to the shader test host. If it merges first, the adapter helpers here move onto its API.
- **#225**: the console flow is also the direction suggested there for the per-lane lane-read bug on every GPU. This PR uses it only for split wave64 programs.
