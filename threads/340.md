# Marvisak/VIctory#340: Feature request: experimental Linux/Wine support and compatibility documentation

- Issue by @ajsem1337, opened 2026-11-24T02:24:28Z, state **open**
- <https://github.com/Marvisak/VIctory/issues/340>
- Archived copy; the original thread is authoritative while it exists.

## Description

I'd like to propose documenting and tracking an **experimental Linux/Wine path** for the Windows build of VIctory. This is a feature/support-tracking request, not a claim that Linux is currently supported or a new regression report against current main.

The Windows-only requirements and the current world-rendering limitations in the README are understood. A separate, explicitly experimental launch recipe and compatibility matrix would help contributors avoid rediscovering Wine-specific setup requirements.

## Tested setup

- CachyOS, kernel 7.3.5; Ryzen 9 5950X, 32 GiB RAM.
- Radeon RX 7900 GRE; Mesa/RADV 26.3.1.
- System Wine 10.0-20260425.
- vkd3d-proton `0bb64c56c8f0dcc` and DXVK `3.1.1-134-g2cb40186c`, from the installed GE-Proton11-11 distribution.
- Windows MSVC build, cross-compiled with Rust 1.98.1 / cargo-xwin 0.24.1.
- **Tested VIctory revision: `97c78d1`**, initially unmodified, then with one small local submission-lock change described below.
- Native Wayland, an isolated Wine prefix, and bubblewrap with networking unshared. Title files were mounted read-only; caches and saves were separate. Audio used the existing Pulse-compatible socket.

**These results are historical:** the reviewed main is `d2a4bae`, 59 commits ahead of the tested baseline. I have not rebuilt or retested that revision.

## What worked

- The completed synthetic D3D12 checks cover compute, native Wayland swapchain/Present, resize and the RGBA8/BGRA8/RGB10A2/RGBA16F format families. Presentation returned `S_OK` for 225 frames, with five exact GPU readbacks.
- A native Microsoft `d3dcompiler_47.dll` in the prefix compiled and ran VIctory's indirect-argument clamp shader. Wine's builtin compiler rejected it. This adds tested workaround evidence to #170; no compiler DLL is attached or redistributed.
- The actual title launched through `victory.exe run ... --execute`. The EXE bound 88 HLE, 427 host and 72 title imports, with **0 missing**; all four title DLLs also bound without missing imports.
- First-time setup, menu/licence screens, settings and saves worked. Menu rendering reached about 30 fps.
- On the next run, existing settings were used and the title went straight into loading the world. Ambient audio became audible, but the scene stayed black. The title's local crash context recorded the game-running state and the first mission's intro. This is **not playable gameplay**.

## Remaining observations on the tested revision

Frame pacing was unstable: roughly 15–30 fps in many logged intervals, with much worse spikes observed manually; audio stuttered. One measured interval spent 55–82 ms preparing/updating textures on the CPU versus about 1–1.5 ms on the GPU.

The unmodified baseline exited with:

```text
a host state prelude did not record (0x8007000E)
d3d12_command_allocator_Reset: There are still 1 pending command lists awaiting execution
```

Moving the existing submission mutex ahead of deferred/prelude preparation changed the pending-allocator error count from 34 to 0 in the next run; that run reached the world and failed differently. **Current main already covers preparation with the submission lock**, so this is not a request to merge the local change or a claim of a new fix.

The next failure exhausted an approximately 1 MiB thread stack. A debugger capture before termination shows many repeated `d3d12core.dll+0x2648f5 / +0x2649f5` frames. The later crash-reporter overflow and the title's null-write report were secondary observations; the exact recursive function has not been identified from the stripped DLL. This may be relevant to #144 / #151, but the AMD/RADV run does not establish the same NVIDIA-driver cause. No kernel GPU reset/fault or device-removal message was recorded in these runs.

## Relation to current work / proposed scope

I found the already-merged texture improvements #60 and #79, Wine physical-page work #53, and the pipeline-worker code now in main. Those changes mean the old timing and failure observations above should not be treated as current-main results. #90 separately tracks native Linux build/test status; #128 and #170 track specific Wine runtime gaps, and #49 collects tester results.

The proposal is to add an experimental Windows-build-on-Linux recipe and track its tested Wine/VKD3D/DXVK versions, prefix/compiler requirements, Wayland/audio setup and remaining limitations separately from official Windows support.

Only diagnostic text is included here. No game binaries, shaders, memory dumps or game assets are attached. Report prepared with AI assistance (Codex).

Update from the same RX 7900 GRE / RADV 26.3.1 box. The biggest change is in **Wine itself**, not VIctory.

## wineserver walks every mapped view on each map and unmap

`perf` inside the sandbox put **37% of the title's CPU time in wineserver**, almost all of it in two loops in `server/mapping.c`:
- `is_valid_view_addr()` (from `map_view`)
- `find_mapped_view()` (from `unmap_view`)

Both walk `process->views`, a plain list. The title's streaming and tiled memory keeps mapping and unmapping physical-page views, thousands of them, so each request walks all of them. This is the same in Wine 10.0, 11.0 and current master. It is the cost that showed up in VIctory's counters as "copies / write-watch" (1.1–1.7 s per world frame).

A small server patch (below) keeps the list and adds an `rb_tree` keyed by view base. Views never overlap, so each lookup is a "highest base ≤ address" descent. I built `wineserver` alone from the exact source of the installed wine-cachyos 10.0-20260425 (protocol 865) and started it inside the sandbox before `wine`. Same VIctory build, same scene:

| per world frame | stock wineserver | patched |
|---|---|---|
| frame time | 3615 ms | **1100 ms** |
| copies / write-watch | 1748 ms | **73 ms** |
| texture preparation | 213 ms | **37 ms** |
| draws | 2097 | **2808** |

The first loading screen now holds a steady 30 fps and loads much faster. I have not yet run Wine's own tests or an A/B against an unpatched build of the same tree, so treat it as a measurement, not a reviewed fix. It should help anything under Wine that maps many views; I'll take it to Wine after that.

Linux/Wine tester here — this path has been running on one box for 45 consecutive boots (RTX 5080, Linux/Wine), so here is a field report on what #3291's guide will want to cover, all measured on the same Wine-modality stack it describes.

**Headline result:** 30 fps through the whole front-end (account picker, wizard pages, legal notices, first-run setup, SETTINGS), 45 boots, **zero first-chance faults and zero device removals** on `victory.exe` under Wine with vkd3d-proton supplying D3D12 and DXVK supplying DXGI. World entry is the wall we're pressing on now; the front-end itself is stable at full rate.

Five things that cost us real time and are not (yet) in the guide:

1. **Headless displays report 0 Hz and one DXGI build dies on it.** On Xvfb (1920x1080 @ 0.00 Hz), Proton 11.0's bundled (Valve-fork) `dxgi.dll` faults `0xc0000094` (integer divide by zero) in the *second* `CreateSwapChainForHwnd`; stock DXVK 3.1.1's `dxgi.dll` handles the 0 Hz mode fine. `dxgi.forceRefreshRate=60` did not help on the bundled build. So the guide's "Wine's own DXGI crashes in wined3d on the first present" is one of *two* known DXGI failure shapes on headless Linux — worth listing both, since the crash offsets differ. Related: keep `WINEDLLOVERRIDES='d3d12,d3d12core,dxgi=n,b'` complete — omitting `d3d12core` gives the wine-builtin stub abort (`unimplemented function d3d12core.dll.D3D12GetInterface`), and never delete `libvkd3d-1.dll`/`libvkd3d-proton-x64.dll` from the prefix — wined3d imports them.

2. **The account picker needs a console-kind pad; keyboard input is inert there.** Under headless Wine the title sits on the account picker facing scripted *keyboard* input (`VICTORY_KEYS`) indefinitely — the HLE merges scripted keys into already-connected gamepads, and the picker is a console-pad-gated screen (`XUserAddAsync` offline-signin path). With a console-class pad enumerating in slot 0 the picker crosses on the first `A`. A tester following the guide with a keyboard-only session will read this as a hang: it is a wrong-input-class park, zero errors in the log. Worth a prominent note; a controller is effectively required hardware for the documented path.

3. **`VICTORY_CACHE_DIR` entries are keyed by the data-dir path.** Rotating `VICTORY_DATA_DIR` to "clean state" silently cold-boots the pipeline cache (the `shaders from the cache` line flips to `hits=0 misses=N` even with the cache dir unchanged), costing ~6-10 minutes of compiling before the first present — which headless looks exactly like a hang. Treat the data-dir + cache-dir as one warm pairing; read the hits/misses line when a boot is slow. The same applies to rebuilds: one of the title's DLL names derives from the build hash, so a new exe can invalidate entries keyed to the old one.

4. **Pin the GPU in both layers, and prove it from the title's own budget line.** The device is created on the default DXGI adapter, so iGPU boxes silently attribute runs to integrated graphics; set `VKD3D_FILTER_DEVICE_NAME` *and* `DXVK_FILTER_DEVICE_NAME`, and a `Found device:` enumeration list in the log is enumeration, not selection. The durable check is the early `video memory as the system counts it` budget line — its numbers name the actual card.

5. **Diagnostics-build gating.** On some trees `diagnostics` is not a default feature and a plain release build compiles the input/capture switches out *silently* — the run looks fully alive (`VICTORY_RELAY` and the fps lines survive) while `VICTORY_KEYS`/`VICTORY_PAD`/capture are inert.
