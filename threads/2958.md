## Description

## Problem

Every store through a heap view sets its 64 KiB page's bit in the write-mark bitmap, and every heap-direct texture read sets its slot's read mark (`Lower::mark_view_write`, `Lower::mark_view_read`). Each is a load of the bitmap word, plus an atomic OR where the bit is clear. The bitmap is a `shared_buffer` in system memory, because the CPU reads and clears it after each submission. So each of those loads crosses the bus, once per lane, for every marked store or read.

Most lanes of a wave write the same page or read the same slot. On an RTX 4070 SUPER the passes that store the most were far slower than the same passes in other trees: a 1.5M-thread clear of three R32_UINT buffers (`a7eeed0646be1ab7`) took 20-41 ms.

Codex pointed at the mark traffic. I confirmed it by moving the bitmap into video memory (GPU upload heap) in a local build. GPU time dropped sharply (`b58eb3ca6ee46427`: 236 → 11 ms per dispatch), but CPU copy-back went to 2.8 s a frame, because the CPU's reads of that memory are uncached. So the bitmap stays where it is, and fewer lanes touch it.

## Change

A lane whose mark bit equals the leading lane's leaves the load and the atomic to that lane; lanes with other bits still set their own (new `lower/marks.rs`, so `lower.rs` stays under the asset-policy size limit). The leading lane is the first active one (`waveReadLaneFirst`, `waveIsFirstLane`), and in pixel shaders the first that is no helper, since a helper's writes are dropped (lowest lane index among non-helpers by `waveActiveOp` min, then `waveReadLaneAt`).

One edge case to address in the newly added pixel-shader branch (`crates/victory-shader/src/emit/lower/marks.rs:19-45`):

- **Out-of-range `waveReadLaneAt` lane index (`u32::MAX`) on all-helper waves**:
  - When a pixel-shader wave reaches `mark_lead(n)` with only helper lanes active (for instance, in unguarded `mark_view_read`, or after `discard`/divergent control flow where only helper lanes remain in the block), every lane produces `key = u32::MAX`, so `waveActiveOp.i32(min, unsigned)` returns `lead = 0xFFFF_FFFF`.
  - Passing `lead = 0xFFFF_FFFF` to `dx.op.waveReadLaneAt.i32(n, lead)` (`marks.rs:38-44`) is an out-of-bounds lane index (undefined behavior in DXIL/D3D12), and if the undefined `f` differs from `n`, helper lanes will also fall through and execute the system-memory bitmap load (`raw_dword`).
  - Guarding the lane index (e.g., clamping `lead` to `0` when `lead == u32::MAX`, and returning `false` for helper lanes via `!helper && (differ || first)` since helper-lane writes are dropped anyway) avoids both UB and unnecessary helper-lane bitmap traffic.
- Adding a pixel-shader test (with helper lanes or a partial quad) plus a divergent-lane test writing two distinct pages/slots would also directly cover both branches of `mark_lead` under `dxil.dll` and GPU execution.
