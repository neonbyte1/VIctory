# Marvisak/VIctory#2465: GPU: the views' written-pages bitmap lives in video memory

- PR by @wbkepler, opened 2026-11-25T14:04:33Z, state **open**
- <https://github.com/Marvisak/VIctory/pull/2465>
- Archived copy; the original thread is authoritative while it exists.

## Description

## What

Translated shaders mark each 64 KiB page they write through views ("Write marks", `crate::shadow::copy_back_marks`) with an atomic OR into one bitmap. That bitmap was a shared buffer in CPU-cached **system memory**. On an NVIDIA host, atomics there cost about 600 times what they cost in video memory: 1M `InterlockedOr` to one dword take 18 ms there and 0.03 ms in video memory. The lanes of a pass writing one region all OR the same few dwords.

The bitmap now lives in **video memory**:

- `shadow::bitmap()` makes a `DEFAULT`-heap UAV buffer (`Host::uav_buffer`), a mapped read-back buffer (`Host::readback_buffer`) and an upload buffer of zeros. It also records one list, once, and closes it: a UAV barrier, a copy of the bitmap into the read-back buffer, `COPY_SOURCE -> COPY_DEST`, and a copy of the zeros over the bitmap.
- A list that binds the bitmap says so (`HostList::marks_views`, from `draw.rs`). `Host::execute` then runs that closed list after the submission's lists, and `copy_back_marks` reads the marks from the read-back mapping. The CPU no longer clears them.
- Lists record nothing more, so there is no extra barrier inside them. The cost is two 512 KiB copies per submission that marks. Two runs of one list in a submission both leave their marks.
- Only the bitmap's last bit (where marks of offsets past it land) is ignored now. Before, the whole last dword was ignored.

Nothing changes in the translator, so shader cache entries stay valid.

**Based on #2175** (`gpu/title-memory-bitmap-in-vram`, which did the same for the title memory page bitmaps in `memory.rs`). This branch includes its commit, for `Host::uav_buffer` / `Host::readback_buffer` and the `memory::tests` shader helper (now `pub(crate)`). Review the second commit only; it rebases trivially once #2175 lands.

## Verification (Windows 11, NVIDIA RTX 5090)

Live runs on an integration build (this change on top of several open PRs needed to reach the world on a 32-lane host). Diag build, same settings and same 300 s script, averaged over 150–285 s in the world (about 4,900 draws per frame):

| | fps | ms/frame | GPU ms | copy-back ms | preparing ms |
|---|---|---|---|---|---|
| before | 2.55 | 395 | 85.7 | 111.8 | 176 |
| this PR | 2.38 | 423 | 85.2 | 115.2 | 201 |

GPU and copy-back time are unchanged within noise in this scene. The frame-time difference is in "preparing", the CPU side, which this change does not touch and which varies about as much between runs of identical builds (another build of the same series measured 2.13 fps / 208 ms there). The marks' atomics are evidently not a large share of the GPU time here. With them in video memory they stay cheap where passes mark heavily, as the microbenchmark shows. Stable: no device removal, and world captures look like before.

A first version gave each list its own bitmap (cleared where the list first used it, read back at its end, as #2175 does). It cost about 5 ms more GPU time per frame (an extra barrier inside each list plus two 512 KiB copies per list), so this version uses one bitmap and one fixed list per submission.

Reviewed — this is a real device-removal fix, not just perf: >2 s marking lists trip TDR, and the 600× atomic-write penalty on a shared-heap buffer explains why. Both bitmaps follow the same sound pattern:

- clear moved GPU-side at list start (zeros copy inside the list recording, so a re-recorded list starts clean — previously the CPU `take` cleared, which only ran if the read-back ran)
- read back at close via UAV→COPY_SOURCE barrier + copy into a mapped readback buffer; CPU side reads it as `const` — no mutation, so the `mem::take` clearing is correctly replaced by the GPU zeros copy
- `marks_views` tracking means `marks_tail` is appended only when a marking list ran, so `copy_back_marks` always reads a populated read-back
- last-bit masking moved from "clear word" to `word & !(1 << 31)` — equivalent on a read-only slice

The video-memory `view_marks_are_read_back_and_cleared_each_submission` test exercises the full path on a real device (runs the marking pipeline).
