## Description

## Summary
Addresses part of #3028 on discrete GPUs where `GPUUploadHeapSupported` is `false` (e.g., NVIDIA RTX 4070 / Ada Lovelace without ReBAR enabled).

### Root Cause
On discrete GPUs without `GPUUploadHeapSupported`, `Host::shared_buffer` (`D3D12_HEAP_TYPE_CUSTOM`, `WRITE_BACK`, `MEMORY_POOL_L0`) and `Host::upload_buffer` (`MEMORY_POOL_L0`) place all shadow buffers, title-memory page tables, and atomic dirty-page bitmaps in system RAM over PCIe. Every shader buffer load, UAV store, page-table lookup, and `InterlockedOr` atomic crosses the PCIe bus instead of hitting local GDDR6X / L2.

### Changes
- **`host.rs`**:
  - Added `Host::is_uma()` (`D3D12_FEATURE_ARCHITECTURE`) and `Host::vram_shadow_budget()` (25% of local `DXGI_MEMORY_SEGMENT_GROUP_LOCAL` budget on discrete GPUs so streaming textures are not evicted).
  - Added `Host::default_uav_buffer()`, reusable 64 MiB `UPLOAD` ring (`upload_vram_copies`), and reusable 32 MiB `READBACK` ring (`readback_vram_copies`) synchronized via `run_copy_list`.
- **`memory.rs`**:
  - Backed `Shared::table` (title-memory page table) and `Bitmap` (title-memory dirty-page bitmap) with `default_uav_buffer` on discrete GPUs, synced pre/post submission via `CopyBufferRegion`.
- **`shadow.rs`**:
  - Backed `shadow::bitmap` (`VIEW_WRITES` / `VIEW_READS`) with `default_uav_buffer` on discrete GPUs.
  - Backed `Shadow` allocations (`find`, `loose`, `Arena`) up to `vram_shadow_budget()` (`<= 128 MiB` per allocation) in `D3D12_HEAP_TYPE_DEFAULT` VRAM with demand-committed `CpuMem` (`alloc_zeroed`) instead of duplicating `L0` D3D12 resources, falling back cleanly to `shared_buffer` once the VRAM budget is reached or on UMA/WARP adapters.

## Measured Results (NVIDIA RTX 4070 12 GB, Windows 11, i9-14900KF)
- **GPU command timing (`VICTORY_GPU_TIMING=1`)** with VRAM-backed shadow buffers + page tables/bitmaps:
  - Total GPU command time: **297.6 ms/frame -> 90.5–91.6 ms/frame (3.25x faster)**
  - Top compute shaders in world scenes dropped from **75.81 ms / 30.22 ms / 19.29 ms / 14.26 ms** down to **< 0.33–1 ms**.
- **Pure release runs with bounded 2.5 GB VRAM budget** (no texture eviction):
  - `on the GPU` (5.1k–5.3k draws/frame): **~405–417 ms -> ~285–323 ms** (total frame time **~545 ms -> ~440 ms**).

### Review (CHANGES_REQUESTED) by @fuzeofficlal — 2026-11-26T20:58:42Z

<https://github.com/Marvisak/VIctory/pull/3312#pullrequestreview-6080415208>

Moving hot shadow buffers, page tables, and dirty bitmaps into `DEFAULT` VRAM on discrete GPUs (`!is_uma()`) while keeping UMA/APU/WARP on shared memory is a great direction, and the `clippy` / `policy` checks and WARP (`UMA=true`) suite pass cleanly.

Testing on a discrete GPU (`NVIDIA GeForce RTX 5090`, `UMA=false`, `vram_shadow_budget=8,236,302,336` bytes, `VICTORY_D3D12_DEBUG=1`) versus WARP (`UMA=true`) and probing an integrated GPU (`AMD Radeon(TM) Graphics`, `UMA=true`) uncovered **four blocking correctness/synchronization bugs** on the discrete VRAM path:

### 1. Silent data loss for marked-page UAV writes (`VIEW_WRITES`) into VRAM shadows (`crates/victory-gpu/src/host.rs:1315-1339`)
`Host::execute` only schedules VRAM -> `CpuMem` readbacks for explicit `Step::GpuWrite` entries before running `shadow::copy_back_marks`. Any shader write through a heap/bindless/marked UAV that sets a bit in `VIEW_WRITES` without a matching `Step::GpuWrite` leaves `Shadow::data` (`CpuMem`) holding the old pre-GPU bytes; `Shadow::copy_back_marked` then compares stale `CpuMem` against title memory and writes back zero bytes.
- **Reproduced live**: dispatching a compute shader writing `0x1337c0de` into a VRAM shadow and setting its `view_writes(false)` bit:
  - RTX 5090 (`is_uma=false`): `gpu_word=0x1337c0de`, **`title_word=0x00000000`** (write lost).
  - WARP (`is_uma=true`): `gpu_word=0x1337c0de`, `title_word=0x1337c0de`.

### 2. Silent data loss for title-memory shader writes via the page table (`crates/victory-gpu/src/host.rs:1315-1339`, `crates/victory-gpu/src/memory.rs:689-691`)
Similarly, shaders writing through the title-memory page table mark pages in `map.dirty` (no `Step::GpuWrite`), and `memory::bind`'s `defer_after` closure calls `copies[k].copy_back_page(at)`. Because those dirty pages are never copied back from VRAM into `copies[k].data` (`CpuMem`) after `sync_vram_post` reads back the dirty bitmap, `copy_back_page` sees unchanged `CpuMem` and writes nothing to title memory. (Existing test `a_submission_that_missed_leaves_the_copies_at_once` did not catch this because its non-missed branch only checked GPU-side `read()`, not CPU `title()`.)
- **Reproduced live** using the `memory::tests::WRITE` shader storing `0xcafef00d` through the page table:
  - RTX 5090 (`is_uma=false`): `gpu_word=0xcafef00d`, **`title_word=0x00000000`** (write lost).
  - WARP (`is_uma=true`): `gpu_word=0xcafef00d`, `title_word=0xcafef00d`.

### 3. Global `ACTIVE_BITMAPS.drain(..)` drops dirty/missed bitmaps across separate submissions (`crates/victory-gpu/src/memory.rs:205, 239-254, 695-703`)
`memory::bind` pushes `(vram, ram)` into the process-global `ACTIVE_BITMAPS` at **record** time, and `sync_vram_post` drains the entire vector on whichever `Host::execute` runs next:
- If lists `L1` and `L2` are both recorded with `memory::bind` and submitted separately (`host.execute(&[&L1])` then `host.execute(&[&L2])`), submitting `L1` drains `L2`'s bitmap too. When `L2` later executes, its VRAM dirty bitmap is never zeroed before `L2` and never copied back to RAM after `L2`, silently dropping both `L2`'s missed-region withholding and its page writebacks.
- Conversely, if a recorded list is reset/dropped without being executed, `ACTIVE_BITMAPS` still holds clones of a bitmap already returned to `BITMAP_POOL`.
- **Reproduced live**: recording `L1` and `L2` (`L2` setting region-1 missed bit in `map2.dirty`), then executing `[&L1]` followed by `[&L2]`:
  - RTX 5090 (`is_uma=false`): **`missed_regions_delta=0`** (`L2`'s miss completely lost).
  - WARP (`is_uma=true`): `missed_regions_delta=1`.
- Fix: associate the `(vram, ram)` bitmap pair with the specific `HostList` (`Deferred`) rather than a global vec, and only zero/read back the bitmaps belonging to `runs`.

### 4. `ID3D12CommandAllocator::Reset` called while previous copy list is still executing (`crates/victory-gpu/src/host.rs:2861, 2959-2970, 2983-3017`)
`upload_vram_copies` submits its final `flush(..., wait = false)` on `static CMD`'s single `(alloc, list)` without signaling/waiting on a fence, and `run_copy_list` unconditionally calls `let _ = alloc.Reset();` on the next call (also discarding `Reset`/`Close` HRESULTs). This immediately violates D3D12 allocator lifetime rules whenever another copy runs before the previous GPU submission finishes (e.g., `Shadow::read_host`/`write_host` calling `flush_test_vram_uploads()` immediately followed by `test_readback_buffer`/`test_upload_buffer`, or `Host::execute(&[])`).
- **Reproduced live on RTX 5090 with `VICTORY_D3D12_DEBUG=1`**: calling `sh.copy(...)` + `sh.read_host(...)` produced **16/16** D3D12 Debug Layer errors:
  `ID3D12CommandAllocator::Reset: A command allocator ... is being reset before previous executions associated with the allocator have completed.` (0/16 on WARP).
- Relatedly, in `flush_test_vram_uploads` (`host.rs:2963-2967`), falling back to `let mut dummy = 0u64;` when `self.submitted.try_lock()` fails can signal the monotonic `self.fence` to `1` while the fence is already past `1`, causing `SetEventOnCompletion(1, ...)` to return immediately without waiting.

### Additional notes
- **Unconditional eager bitmap allocation & extra fence wait per submission (`crates/victory-gpu/src/shadow.rs:970-975`, `host.rs:2798, 2867`)**: `has_vram_bitmaps()` calls `bitmap(false)` and `bitmap(true)` on every `Host::execute`, eagerly allocating both bitmaps on the first submission and forcing both `upload_vram_copies` and a second synchronous `readback_vram_copies` + fence wait on every single submission on discrete GPUs even when no shader uses view write marks or VRAM shadows. Consider checking whether either `OnceLock` is actually initialized (and whether the submission used view marks/reads) instead.
- **Budget accounting race & leak (`crates/victory-gpu/src/shadow.rs:133-157`)**: `try_vram_shadow` checks `VRAM_BYTES.load(Relaxed) + size > budget` before `fetch_add` (non-atomic TOCTOU across threads), and if `CpuMem::new(size)` fails at line 154, `VRAM_BYTES` is never decremented. Also note `Shadow::peek` (under `diagnostics`) still reads `self.data` without a VRAM readback.

### 1. Concurrent title + GPU writes merged in `Shadow::copy_back` and `Shadow::copy_back_marked` never upload the merged bytes back to VRAM
- `crates/victory-gpu/src/shadow.rs:585-600` (`copy_back_or_not`) and `crates/victory-gpu/src/shadow.rs:659-669` (`copy_back_marked`)

When both the GPU and a title thread write different offsets of the same 64 KiB page during a submission, `merge_writeback(...)` copies the title's new bytes into CPU `self.data` (`CpuMem`) and then `t.taken(...)` marks the page clean in `Tracked`. Because `self.queue_vram_upload(...)` is not called, the VRAM buffer (`self.buffer`) keeps the stale pre-merge bytes, and subsequent `Shadow::refresh` / `Shadow::update` calls return `0` immediately (`self.clean() == true`), leaving the title's concurrent write permanently invisible to the GPU.

Live reproduction on RTX 5090 (`is_uma = false`) vs WARP (`is_uma = true`) — initial page `[0x11111111, 0x22222222]` (and `[0x33333333, 0x44444444]`), submission 1 writes word 0 on GPU while the title writes word 1 (`0xbbbbbbbb` / `0xdddddddd`), submission 2 calls `refresh` and reads both words in a compute shader:
- RTX 5090 (`copy_back`): `title_after_s1 = [0xaaaaaaaa, 0xbbbbbbbb]`, `clean = true`, `gpu_saw_s2 = [0xaaaaaaaa, 0x22222222]` (expected `[0xaaaaaaaa, 0xbbbbbbbb]`)
- RTX 5090 (`copy_back_marked`): `title_after_s1 = [0x1337c0de, 0xdddddddd]`, `clean = true`, `gpu_saw_s2 = [0x1337c0de, 0x44444444]` (expected `[0x1337c0de, 0xdddddddd]`)
- WARP: both return the expected merged words.

Calling `self.queue_vram_upload(at as u64, n as u64)` right after `merge_writeback(title, host, old)` in `copy_back_or_not` and `self.queue_vram_upload((from - start) as u64, n as u64)` in the `Some(before)` arm of `copy_back_marked` resolves both cases (verified live on RTX 5090: both submissions read back `[0xaaaaaaaa, 0xbbbbbbbb]` and `[0x1337c0de, 0xdddddddd]`).

### 2. Existing `shadow::tests::` fail under default parallel test execution on discrete GPUs (`self.event` / `CMD` / `VRAM_UPLOADS` / `BITMAPS` races)
Running `cargo test --locked -p victory-gpu --features diagnostics -- shadow::tests::` on RTX 5090 fails 3/3 times (while passing 10/10 on WARP and 10/10 with `--test-threads=1`):
- `shadow::tests::bytes_off_the_runtimes_memory_are_copied_at_each_use` (`shadow.rs:1690`): `left: [0], right: [4660]`
- `shadow::tests::title_writes_under_a_busy_range_are_copied` (`shadow.rs:1625`): `left: 0, right: 85`

There are three concurrency bugs interacting here:
1. `Host::run_test_copy_sync` (`crates/victory-gpu/src/host.rs:2989-3005`) calls `self.run_copy_list(record, None)` (releasing the `CMD` mutex before GPU execution finishes, allowing another thread to reset `CMD`'s allocator while in flight) and then waits on the shared auto-reset `self.event` (`host.rs:3002`) without holding `self.submitted`, violating `Host`'s safety contract (`host.rs:69`) and racing with `Host::execute` / `run_copy_list` (`host.rs:3072`). Giving `CMD` its own private event handle created alongside its dedicated `fence` and having `run_test_copy_sync` pass `Some(0)` into `run_copy_list` keeps allocator reset and wait serialization strictly inside `CMD` (and avoids re-entrant deadlock on `self.submitted` when `write_host` runs inside `defer_host`).
2. `Host::flush_test_vram_uploads` (`host.rs:3019-3025`) drains global `VRAM_UPLOADS` and flushes without serializing concurrent callers: thread B can drain thread A's pending upload, and thread A then observes an empty queue and reads zeroed VRAM before thread B's copy finishes. Holding a dedicated mutex across `take_vram_uploads()` + `upload_vram_copies(...)` in `flush_test_vram_uploads` eliminates this race.
3. `shadow::tests::vram_marked_view_writes_go_back_to_title` (`shadow.rs:1949`) submits via `Host::execute` while other `shadow::tests` (`marked_pages_go_back_by_the_bytes_the_gpu_changed`, `marks_of_shaders_using_title_memory_are_held_back`) concurrently mutate and clear the global `BITMAPS` via `copy_back_marks(...)` without serialization, causing intermittent `left: 0, right: 322420958` failures in parallel runs. (Also note that `vram_marked_view_writes_go_back_to_title` uses `copy_w.write_host(...)`, which writes to CPU `self.data` as well as VRAM, so it would still pass even without VRAM readback; writing only to `copy.buffer` on the GPU via `CopyBufferRegion` from an upload buffer makes the regression test strictly exercise `vram_marked_reads`.)

### Minor note (non-blocking)
- In `Host::execute`, `readback_vram_copies` (`host.rs:1357`) runs before `GetDeviceRemovedReason()` (`host.rs:1380`). If the main submission triggers device removal, `alloc.Reset().expect(...)` inside `run_copy_list` (`host.rs:3061`) can panic before `Host::execute` reaches `fail(...)` and reports DRED breadcrumbs / `removal_data(runs)`. Moving the `GetDeviceRemovedReason()` check ahead of the VRAM readback block preserves crash diagnostics.

However, live discrete-GPU testing uncovered two remaining blocking issues:

### 1. Permanent silent VRAM data loss when `merge_writeback` returns `false`
- `crates/victory-gpu/src/shadow.rs:27-37` (`merge_writeback`), `crates/victory-gpu/src/shadow.rs:585-601` (`copy_back_or_not`), `crates/victory-gpu/src/shadow.rs:661-674` (`copy_back_marked`)

`merge_writeback(title, host, old)` updates `*host_byte = *title_byte` to absorb concurrent CPU writes into the CPU staging slice (`self.data`) unconditionally, but its `bool` return value only reflects whether any byte in `title` changed (`changed != 0`). Both `copy_back_or_not` (line 588) and `copy_back_marked` (line 668) only call `self.queue_vram_upload(...)` when `merge_writeback` returns `true`, yet both still unconditionally mark the 64 KiB page clean via `t.taken(...)` right afterward (lines 591/601 and 672-674).

On a discrete GPU (`copy.vram == true`), whenever CPU staging absorbs CPU writes while `merge_writeback` returns `false`, `t.taken(...)` clears the dirty bit without queueing a VRAM upload, so subsequent `Shadow::update()` calls return `0` and VRAM permanently retains stale pre-CPU-write data. Reproduced live on discrete hardware (`is_uma=false`, `copy.vram=true`):

An ordering case another tree hit with the same kind of budget (read from this head `576188a` and that tree's code; not run here).

`try_vram_shadow` admits copies first come, first served, up to 25 % of the local budget (`vram_shadow_budget`), and every backing up to 128 MB may take a share. ZigZagBoi1/ScarlettPort (a VIctory-derived tree) had the same shape with a 512 MB card-copy cap. It is an ordinary card copy otherwise, and their four-fifths-of-the-card rule still applies. One log line when `try_vram_shadow` first turns a buffer down (its size and the bytes used) would show whether it happens. A reserve for large buffers, or admission by how often a buffer is read rather than by arrival, would keep the late big ones from losing out.
