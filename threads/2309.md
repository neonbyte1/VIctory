## Description

**Stacked on #439** (r4tedx; it contains #233 and #320). The two commits on top of it are the change. The first is powplusplus's `d48ec76` from #1885, cherry-picked with its author kept; the second is ours.

## Problem

On NVIDIA (32-lane waves) under Wine/Proton, vkd3d-proton converts each pipeline's DXIL to SPIR-V with dxil-spirv, inside the title's process. Some of #439's console-flow programs have a block that branches back to **two** loop headers, e.g. `br c, 191, 126`, where 191 is the inner loop's header and 126 the outer one's. Others have a loop header with three back edges.

dxil-spirv's structurizer expects one back edge per block and per header ("DXIL seems to obey this", `forward_visit_resolve`). It reads the extra edge as a forward edge, makes a cycle, and recurses until the stack runs out (`LoopMergeTracer::trace_from_parent`, about 100k frames). With a large stack it uses memory instead (40 GB before I killed it), or the pipeline thread hangs. In the title, the process ends while those pipelines are created, or no pipeline ever finishes.

`main` has the same shapes in 7 programs. They convert because those programs have no `WaveReadLaneAt`, and dxil-spirv only walks the graph before fixing it up in `flatten_subgroup_shuffles`, which runs only when a shader reads other lanes. #439 adds the lane reads, and then the same shapes are fatal.

## How it was found

1. **The pipeline journal (#491, `VICTORY_PIPELINE_JOURNAL=1`).** On #439 the title's process died during world load, with no crash log and no GPU fault. The journal's pending notes named the pipelines being created at that moment: `b2ff2ef0d6c98dd7`, `fdd56d97a806bcca`, `32ed072b9f845048` and others.
2. **Offline reproduction.** Their containers came from the title's `shaders.rpf` and were translated with #439. A native dxil-spirv build, capped in memory, then crashed on them the same way: it reached 40 GB uncapped and overflowed the stack when capped. gdb showed the recursion (`LoopMergeTracer::trace_from_parent`, about 100k frames).
3. **The cause.** Diffing the DXIL against `main` showed the block that branches back to two loop headers.
4. **Confirmed in the title** with #2292 (`VICTORY_PIPELINE_SOFT_CRASH=1`). Without this fix, the same two programs are caught as stack overflows (`0xc00000fd`) inside vkd3d-proton.

## Change

All in `crates/victory-shader/src/emit/bitcode.rs`:
- **`364c1bc`** (powplusplus, from #1885): `Module::single_latches` gives each loop header one back edge.
- **`91e3bdf`**: a block that branches back to two headers sends its edge to the outer header through a new block of its own, fixing that header's phis. The block stays the inner loop's exiting latch, as DXC makes them. The empty-latch fold at write time no longer folds a latch into a block that already branches back, which would undo the split.

The change is generic: `lower.rs` and `wave.rs` are untouched, so it should not conflict with #2214.

## Tested

- **dxil-spirv (native build, capped at 3 GB):**
  - Before: it crashes on `fdd56d97a806bcca` (`InstanceCulling:CS_Prop_BatchNoCull`) and `32ed072b9f845048` (`deferred_tiled:CS_LaserLightShadowRaytracing`).
  - After: both convert, pass `spirv-val`, and `vkCreateComputePipelines` returns `VK_SUCCESS` on native NVIDIA (RTX 5080, no Wine).
- **All 413 dumped programs of the title:** only the 8 with these loop shapes change, and the other 405 give byte-identical output. All 8 convert and create on NVIDIA (0.3–1.5 s each).
- **In the title** (RTX 5080, Linux, Proton with vkd3d-proton 3.2.0): with #439 alone, the process died or the pipeline workers stalled while these pipelines were created. With this change, all of them create, including the five large `*:CS_RaytracingResolve` programs, and the run goes past that point.
- `cargo test -p victory-shader --lib`: 151 passed on Linux, and 178 passed, 0 failed for the Windows build under Proton on the RTX 5080. That includes the new `a_block_branching_back_to_two_headers_gets_one_back_edge` and `empty_latches_to_two_headers_fold_once`.
- `cargo clippy -p victory-shader --all-targets -- -D warnings`: clean.
