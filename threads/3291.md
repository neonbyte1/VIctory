## Description

A setup guide for testers on Linux, in response to #340: `docs/linux-wine.md`. It describes how VIctory's Windows build is cross-compiled and run under Wine with vkd3d-proton (D3D12) and DXVK (DXGI). It's for testing, not a supported release.

**What it covers:**
- **Building:** cross-compiling for `x86_64-pc-windows-msvc` with clang-cl and an `xwin` splat.
- **Prefix setup:** the GE-Proton11-14 DLLs, and crash dialogs off.
- **Running:** a headless gamescope run.
- **Caches:**
  - never `VKD3D_SHADER_CACHE_PATH=0`: with it, runs start with minutes of pipeline backlog and drop draws until it drains;
  - NVIDIA's shader disk cache size.
- **NVIDIA specifics:** 32-lane waves (#439 with #2118; the optional #2176 stack), the view-heap cap (#747), and not running GPU tests beside the game.
- **Unmerged PRs that a working NVIDIA/Wine build needs today:** a dated table with what breaks without each.
- **Tests:** running the suite with `cargo xtask wine-test` (#1218), and the known Wine gaps with the PRs that fix them.

Every statement was checked against the code, the PRs (state as of 2026-11-26) or our own runs on an RTX 5090. Anything I couldn't verify was left out. No game files, paths or personal setup details are included. The PR table will go stale as PRs land; it says so and is dated.

```markdown
## AMD specifics (RADV)

Measured on one machine: RX 9070 XT (16 GB), Ryzen 9 5950X (two CCDs of eight cores), CachyOS,
Mesa 26.3.1 RADV, GE-Proton11-14, vkd3d-proton master; Series X profile at 4K, ray tracing on.
The runs used forks of VIctory, not this repository's `main`; these points do not depend on the tree.
Full notes: https://github.com/Anzymanz/VIctory-ox/blob/main/docs/linux-findings.md

* **wineserver.** The stock server walks every view of the process on each map and unmap
  request, and the title keeps tens of thousands of views mapped: the world ran about eight
  times slower here (a median world frame of 8,442 ms against 1,041-1,061 ms with the fix).
  CachyOS/wine-cachyos#50 keeps the views in a tree; LooperSalty/AnyXboxX#261 builds that
  server for GE-Proton11-14. GE-Proton's own tree carries an equivalent fix since `d3b6ae7`,
  so a GE-Proton release after 11-14 that includes it needs no local build.
* **Leave `power_dpm_force_performance_level` on `auto`.** Forced to `high`, the RX 9070 XT
  stayed at 2.4 GHz against 3.4 GHz on `auto`, and GPU time per frame tripled.
* **Check the GPU clock.** Under VIctory's bursty submissions the driver can read the load
  as light and run the card at half clock (1.6 against 3.3 GHz here, about six times the GPU
  time per frame). `pp_dpm_sclk` under `/sys/class/drm/card*/device/` shows it.
* **Both CCDs.** The title gives its threads console affinity masks, and under Wine these land
  on both CCDs of a two-CCD Ryzen whatever `taskset` the launch used (of 184 threads, 110 were
  unrestricted and 39 held to one CCD). A `WINE_CPU_TOPOLOGY` map that shows the game one CCD
  keeps it there but gained nothing we could measure (244 and 192 ms a frame against 219 and
  216), nor did a map that pairs each core with its SMT sibling (mean 146 ms over four runs
  against 154 over six, inside the spread). Holding every game thread to one CCD cost time: in
  an on/off test inside one run (20 phases of 8 s) it was 8.6 ms a frame slower (124.7 against
  116.0 ms, slower in 9 of 10 pairs). Leave the game on both CCDs.
* **Run-to-run spread.** Identical whole runs differed by up to 50 ms a frame while other
  programs were busy; alternate off and on runs, as above, before trusting a difference.
  Most of the frame times above come from runs that also saved a picture every 8th frame, in
  both arms of each comparison: the differences stand, but the absolute times include that cost.
```
