## Description

Under Wine and Proton, 16-bit depth that the title writes through unordered views never reaches the host's depth texture (#1860). It is moved by a compute converter compiled at run time. Wine's built-in `d3dcompiler_47` (vkd3d-shader) refuses it, because it has no `Load`/`Store` on byte address buffers, and it ignores the `RootSignature` attribute. The converter is never made.

#1872 serializes the root signature when the compiler drops it. That is half of it: with Proton-CachyOS 11.0's compiler the shader still fails on `buf.Load`, and #1872's own test fails there too. This PR does both halves, the way #2913 does for the indirect clamp:

- The buffer becomes a structured buffer of `uint`, indexed in words. Every offset and pitch comes from a placed footprint: offsets are 512-byte aligned, row pitches 256.
- The root signature is serialized beside the shader, in the order the caller sets it.

The odd-width test runs the converter both ways on a 3-wide surface, with a distinct value per texel and a sentinel in each row's padding. It is adapted from #1872's test.

This PR also includes #3064's exact UNORM16 midpoint rounding and its exhaustive GPU test, with the original commit author preserved. The combined shader omits `[RootSignature(RS)]` because the root signature is serialized in Rust. That avoids the undeclared `RS` error @neonbyte1 found when integrating the two PRs.

Fixes #1860. Supersedes #1872.

## Proof

On the combined head, both converter tests passed on an RX 9070 XT (RADV) using Proton-CachyOS 11.0 and Wine's built-in `d3dcompiler_47`. The midpoint test found zero mismatches across 393,216 inputs. Strict `victory-gpu` Clippy passed with default and all features for `x86_64-pc-windows-msvc`.

The Wine compatibility change was also tested before integrating the rounding commit.

`victory-gpu` tests cross-built for `x86_64-pc-windows-msvc`, run under Proton-CachyOS 11.0 with vkd3d-proton 3.2.0 on an RX 9070 XT (RADV):

- **Wine's built-in compiler:** the new test passes. With `main`'s shader swapped back in, it fails because the converter is never built. With the odd-width tail guard removed, it fails on the padding sentinel.
- **Microsoft's `d3dcompiler_47` 10.0.26100:** the new test passes. The whole suite has the same 3 failures as `main`. They are vkd3d-proton issues fixed by #1722 and #2101.
- **Clippy:** `cargo clippy -p victory-gpu --all-targets --target x86_64-pc-windows-msvc -- -D warnings`, with and without `--all-features`, is clean. CI runs the Windows tests.

A merge note for @andrewpozdnakov7-jpg and @arogan178 (#2919): these two PRs conflict without git noticing. #2919 removes both `#define RS` and `[RootSignature(RS)]` from the depth converter, because Wine's compiler builds it and the code makes the root signature beside the shader. #3064 keeps the `[RootSignature(RS)]` line. When both are merged, the attribute stays with no define. Wine's `D3DCompile` (vkd3d-shader) then rejects the converter with `E5005: Identifier "RS" is not declared`, and no depth converter exists: the log says `no depth conversion: 16-bit depth written through unordered views does not reach the depth texture`. In game on my fork's integration (RTX 5090, Wine 11.22 + vkd3d-proton), character close-ups get soft, skin-coloured blocks over the hair and back, and the PR's own `float_depth_rounds_at_each_u16_threshold` fails with `depth converter`.

The fix is to drop the attribute in whichever PR lands second and keep #3064's `u16()` as is: https://github.com/neonbyte1/VIctory/commit/634bcce5 (adds a CPU test that the converter source compiles without it). With that on the same tree:
- `float_depth_rounds_at_each_u16_threshold` passes under Wine/vkd3d-shader, with **0 of 393 216** values misrounded. The previous `(x * 65535 + 0.5)` rounding misrounds 32 768 of them, the first at `0x37000080` (expected 0, got 1). So #3064's rounding is worth having on this compiler too.
- In game, the blocks are gone at frames 1700 and 2048.

One unrelated note: `depth_typed_and_default_uavs_write_through_the_twin` fails under Wine with 0x80004005 both with and without these changes.
