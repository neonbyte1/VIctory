## Description

Seven places in the frame paths that cost allocations, locks or system calls per call site rather than per frame. Each one comes from a number in the diagnostics profile of a world frame (`copystat`, 8 137 draws a frame), and each is independent.

1. **`victory-gpu: read a copy-back's title bytes into a pooled buffer`** - `copy_back_page`, `copy_back_or_not` and `copy_back_marked` made a fresh `Vec` of up to 64 KiB for the bytes they read from title memory. The frame report counted **~1 900 page faults per frame** in copy-back alone, from committing those buffers from scratch. They come from the pool the snapshots already use and go back to it; the pages a copy-back took are filtered in place instead of being collected into a second `Vec`.
2. **`victory-gpu: sync a heap's slots in passes, without a vector of them`** - `HostHeap::sync_slots` collected every slot's record into a `Vec`, then a `Vec<bool>` of which name a current view, then a `Vec` of the differing slots. A world frame asks about **806 912 slots** (`copystat`: "heap slots the title copied"), so that is tens of megabytes of allocation per frame for records read once. 512 slots at a time in stack buffers now; `views_current` fills a slice.
3. **`victory-gpu: let heap readers share the shader heaps' lock`** - `SHADER_HEAPS` guards the list of shader-visible heaps. Every title thread that writes a view and every submission's heap sync only ever *read* it, but they took turns on a mutex, and the frame report put **48 ms per world frame** into title threads waiting for it. Readers share an `RwLock` now; a heap's release still takes it alone and waits for readers, so a heap cannot be freed under a sync.
4. **`victory-gpu: ask how many ranges shaders are writing before the lock`** - `Shadow::update` runs for every refreshed range (tens of thousands a frame) and locked `pending` to see whether the range meets a range shaders write. Most meet none, and the set is empty outside the window between a GPU-write step and the copy-back. An atomic count answers that without the lock.
5. **`victory-gpu: keep a view's generation away from the view`** - `Views::list` held `(View, u32)`, so the per-slot question "does this record still name a current view" touched a whole `View` (tens of bytes) for 4 bytes of generation. The generations live in a `Vec<u32>` of their own now: one 4-byte read per slot, and the view itself only for the few hundred slots that get mirrored.
6. **`victory-watch: give write access back to guarded pages in runs`** - `open` gave access back one page at a time, a `VirtualProtect` each: the frame report counted **13 624 pages opened** and **75.95 ms in the guard handler**. Consecutive guarded pages are given back in one call, both where a write of ours opens what it covers and where a released tracker opens what nothing else watches.
7. **`victory-gpu: keep a shader's user data on the stack`** - the dwords a stage's user data sets were collected into a fresh `Vec` for every stage of every draw (up to 64 dwords). They live in an array on the stack now; a title that asks for more still gets a `Vec`.

What is measured and what is not: the per-item numbers above are from the diagnostics build's own counters (they pointed at these call sites). The frame-time effect of the stack as a whole is not measured yet - this machine's world frames are TDR-prone and other GPU clients share the adapter, so the plan is one A/B run of the whole stack (diagnostics build, same save, `copystat` before/after) before anything else here is extended. Nothing in the patches changes what a frame does, only how it does it; `cargo test --workspace` passes (228 in `victory-gpu`), clippy is clean.

The tier below this one is design-level and is **not** in this PR: `ReadProcessMemory` of 205 MB a frame (117 ms), per-page `VirtualProtect` of the write watch (40 ms) and the 61 MB of snapshots for ranges shaders write (45 ms).

### Two issues found
1. **`6319997` (`Shadow::pending_len` fast path in `shadow.rs`)**: `writing()` drops the `self.pending` mutex before calling `self.pending_len.fetch_add(1, Ordering::Relaxed)`, and `update()` reads `pending_len` with `Ordering::Relaxed` outside the lock. If `writing`/`copy_back`/`update` ever overlap across threads, `update()` can observe `0` right after an insert (or `copy_back` can `remove` + `fetch_sub` before `fetch_add`, underflowing `pending_len` to `usize::MAX`), and `Relaxed` establishes no happens-before edge with `pending`. Updating `pending_len` **while holding the `pending` mutex** with `Release` (and reading with `Acquire` in `update()`) closes both the race and ordering gap at zero extra lock cost.
2. **`2851648` (`watch::open_runs` in `watch.rs`)**: `open_runs` removes `[first, last)` from `g.protected` and issues a single `VirtualProtect(..., PAGE_READWRITE)` ignoring the return value. On Windows, `VirtualProtect` fails with `ERROR_INVALID_ADDRESS` (`487`) across adjacent `VirtualAlloc` regions or uncommitted pages (verified locally on Windows 11: 128 KiB across two contiguous 64 KiB `VirtualAlloc` blocks returned `0`, `err=487`), leaving the whole run `PAGE_READONLY` after dropping it from `g.protected` -> unhandled `0xc0000005` on next write. Checking the return value and falling back to per-page `VirtualProtect` (matching `protect_noting`) fixes it. Also conflicts directly with #2849 in `watch.rs`.

Review note on item 6 (`open_runs`), from the same failure found in #2849 (now closed as a duplicate of this item).

**Bug:** `VirtualProtect` can return 0 with `ERROR_INVALID_ADDRESS` (487) when the run crosses two separate `VirtualAlloc` reservations/allocations, even when the pages are contiguous and all present in `g.protected`. `open_runs` removes each page from `g.protected` before the call and ignores the `BOOL`. On failure the pages are still read-only but are no longer guarded; the next write faults and can end in an access violation.

**Suggested shape:** do not make the batch authoritative without checking its result.

```rust
let mut old = 0;
let batch = unsafe {
    VirtualProtect((first * PAGE) as *const _, (last - first) * PAGE, PAGE_READWRITE, &mut old)
} != 0;
if !batch {
    // Separate allocations: one page at a time, as the old `open` did.
    for page in first..last {
        let mut old = 0;
        unsafe { VirtualProtect((page * PAGE) as *const _, PAGE, PAGE_READWRITE, &mut old) };
    }
}
```

Either keep the pages in `protected` until the batch succeeds and only then remove them, or remove them and rely on the per-page fallback. Keep the `OpenPages` diagnostic count for the pages actually opened.

**Reproduction test:** two adjacent 64 KiB `VirtualAlloc(..., PAGE_READONLY)` regions, add both pages to `g.protected`, call `open_runs`; without the fallback the 128 KiB batch fails 487 and both pages stay read-only; with it both become `PAGE_READWRITE`. `writable()` in `watch::tests` can assert the result. This was reproduced on Windows 11 by @fuzeofficlal; I have not pushed a competing branch.

<https://github.com/Marvisak/VIctory/pull/2848#issuecomment-7193613464>

Both confirmed bugs are fixed on the branch, each as its own commit.

**`4a195c94` - a guarded page leaves the guard set only once the kernel opened it.** `watch::open_runs` removed each page from `Guards::protected` *before* `VirtualProtect` and ignored the result. A page that only left the set that way stays read-only for good (no tracker holds it any more, so nothing opens it again) and the title's next write there faults with no guard to take it - the Wine removal `crashbashash` reproduced. Now:

- the set is not touched until the protection is off;
- a run the kernel refuses (a range crossing two allocations, 487) is retried one page at a time;
- pages it does open leave the set, the rest stay in it for the next take or the fault handler;
- what did not open is logged once per run, and `copystat`'s "pages opened" counts what actually opened.

**`50be8a7c` - the pending-range count moves under its lock.** `Shadow::writing` inserted into `pending` and then bumped `pending_len` after the mutex was released, while `copy_back` reads that count to choose the fast path ("nothing pending"). A reader could see 0 with a range already in the set, take the snapshot path without it, and the count could drift below the set's size. The bump is now inside the lock the set moves under; add/sub are `Release`, the load `Acquire`.

Verification: `cargo test --release -p victory-gpu` - 228 passed, 1 ignored; clippy `-D warnings` clean on the crate and its targets. One GPU test failed once in a full run and passed alone and in the next full run (`draw::tests::a_texture_is_uploaded_once_per_submission_and_only_when_written`), so it is the load-sensitive kind this machine has, not these changes.
