# Marvisak/VIctory#2723: Shader: key every heap handle cache by element type (#177 on main, fixes the NVIDIA compute-pipeline crash)

- PR by @andyeox-systemd, opened 2026-11-25T18:50:30Z, state **open**

## Description

Builds on #177 (Ortomanic's fix and gingertonik's test, credited as co-authors), resolved against current `main` (`13f91ca`), and extended to the two handle caches `main` added since.

## The bug

When a UAV is read as float and is also the target of an atomic, the lowering reused one float-typed handle for both. After conversion to SPIR-V, the atomic is invalid (`AtomicOr` / `AtomicUMax: expected Result Type to be integer scalar type`), and NVIDIA's compiler crashes in `vkCreateComputePipelines` (`0xc0000005` / `0xc000001d` in the Unix call). This is the crash in #144.

#177 added the element type (`props.1`) to the `handles` key. `main` has since added `entry_handles` and `join_handles`, which had the same problem, so this PR keys those by both property words as well. #177's test is included, with `view_marks` added for the current `Parts`.

## Separate vkd3d-proton issue

On vkd3d-proton 3.1 and earlier, the title crashes earlier for a different reason. dxil-spirv's old structurizer emits invalid control flow for three shaders ("Function end cannot be called in blocks", "block exits the loop headed by…"). Microsoft's `dxv` accepts our DXIL for all three, so that's not a VIctory bug. It is fixed by dxil-spirv's structurizer rewrite, which is in vkd3d-proton master and not in 3.1. NVIDIA under Wine needs both fixes.
