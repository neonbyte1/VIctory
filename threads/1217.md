# Marvisak/VIctory#1217: GPU: the copies timing no longer counts the flush before a title copy twice

- PR by @neonbyte1, opened 2026-11-24T16:28:54Z, state **open**
- <https://github.com/Marvisak/VIctory/pull/1217>
- Archived copy; the original thread is authoritative while it exists.

## Description

The `copies` figure on the frame-rate line counts some refresh time twice.

`HostList::run_deferred` starts a timer before each step. For `Step::Copy` it then calls `batch.title_written()`, whose `Batch::flush` already adds each pending refresh's time to `PREPARING[0]`. The step then adds `started.elapsed()`, which includes that flush again. `Step::Run`'s `RunUs` counter (diagnostics) also included the flush.

The timer now restarts after the flush in both places. Nothing else changes: the copies themselves, the order of the steps, and every other counter are as before. The reset in the `Run` arm is behind the `diagnostics` feature because only `RunUs` reads it there.

### Why it matters
In world frames with thousands of small title copies per frame, the double counting made `copies` look several times larger than the work behind it. That misattributed the CPU cost of world frames.

Measured on an RTX 5090 under Wine 11.22 + vkd3d-proton (prologue, ~3,100 draws/frame, medians over ~55 summary lines):

| Build | `copies` ms/frame | ms/frame | Unmapped MB/frame | Fallbacks/frame |
|---|---|---|---|---|
| Before (main + other open PRs) | 96.4 | 324.9 | 351.9 | 1,331 |
| After, with #514 also merged | 21.4 | 255.8 | 5.8 | 135 |

The frame-time drop comes from #514; this change only removes the double count from `copies`.
