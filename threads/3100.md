## Description

D3D12 allows at most 65,535 thread groups per dimension per dispatch, and the indirect clamp cuts larger counts to that. GTA VI asks for more. `indirect_diffuse_lighting:CS_FinalGather` (`2dc364df5d3278b8`) dispatches 74,192 to 83,008 groups in x depending on the view, 8 per screen tile. With the clamp, about 1,000 tiles at the end were never gathered. The bottom rows of the lit picture showed stale tile content from earlier frames, a band of coloured blocks along the bottom edge.

**Stacked on #2969** (this extends its Wine-compilable clamp) **and #3097** (`lower.rs` tests in their own file, for room under the 512 KiB limit). Please review from `GPU: split compute dispatches past 65,535 groups in x` on.

**What changes:**
- **Translator.** A compute shader that reads TGID x adds a group-id base: one dword in `b0` of register space 3 (`GROUP_BASE_SPACE`), loaded once in the entry block. Mesh shaders, y and z are unchanged.
- **Direct dispatch.** For such a pipeline, the host sets the base as a root constant and dispatches at most 65,535 groups at a time. Pipelines whose shaders don't read TGID x dispatch as before.
- **Indirect dispatch.** The clamp expands each dispatch record into 17 records of `{base, x, y, z}`. 17 × 65,535 covers the clamp's 2^20 limit. They execute through a command signature `[CONSTANT base, DISPATCH]` made for the pipeline's root signature, with the title's count multiplied by 17. Empty chunks dispatch nothing.

**Census** over the title's shader pack (`VICTORY_EMIT_DUMP`, byte comparison of every emitted program, before and after on this branch):

|---|---|---|

The same programs fail to translate before and after (227).

**In game** (Linux: GE-Proton11-14 Wine, vkd3d-proton, RTX 5090 driver 620.73.04; prison yard, frames 1450–1700). I measured the share of bright blocky pixels in the bottom 4% of the frame:

| this PR | 0% in all 11 captured frames, 3 runs |

The diagnostic switch only confirmed the cause. It isn't something to ship: NVIDIA's Vulkan driver happens to accept more than 65,535 groups, but D3D12 drivers needn't.

With the fix, the lit yard looks the same as with the cap lifted. There was no device removal or Xid in any run.

**Tests**, under `cargo xtask wine-test` (#1218) on the same machine: `indirect` 8/8 and the new tests below. `cargo clippy --workspace --all-targets` (with and without `diagnostics`) and `cargo xtask policy` are clean.
- `chunked_dispatch_records_hold_every_word`: `[140000, 1, 1]` becomes bases 0, 65,535 and 131,070 with x 65,535, 65,535 and 8,930, then 14 empty chunks, count 17.
- `group_base_covers_a_dispatch_past_the_host_limit`: 70,000 groups, direct and through `ExecuteIndirect`. Every one of the 70,000 output words is written once.
- A lowering test that only compute TGID x gets the base.

**Limits:**
- The GPU test dispatches an HLSL shader that binds the base the way the translator does, not a translated GFX10 program. The translator side is covered by the lowering test and the census.
- I have no Windows machine. The changed root signatures (one more root constant for those compute pipelines) haven't been run on a native D3D12 driver.

### Review (CHANGES_REQUESTED) by @fuzeofficlal — 2026-11-26T08:40:02Z

<https://github.com/Marvisak/VIctory/pull/3100#pullrequestreview-6070845111>

Covering `ExecuteIndirect` for compute dispatches past 65,535 groups in `x` is genuinely useful (building beyond `#3086`, which handles direct dispatches), and the clamp + `[CONSTANT, DISPATCH]` command-signature idea is the right direction. However, reviewing `6d3848e0` line by line and testing natively on Windows 11 (RTX 5090, WARP, and Windows SDK `fxc.exe`) turned up several blocking bugs, including a silently skipped test:

### 1. Accidental deletion of `|| self.memory.is_some()` in DXIL emission (`crates/victory-shader/src/emit/shader.rs:630-633`)
Replacing `|| self.memory.is_some()` with `|| self.group_base.is_some()` omits the entire `!dx.resources` emission for any shader whose only resource is read-only title memory (`self.memory.is_some()`, e.g., a VS/PS/MS or a CS that does not read TGID `x` and has no user data/samplers/root views/view marks). Please keep `|| self.memory.is_some()` alongside `|| self.group_base.is_some()`.

### 2. Counted `ExecuteIndirect` still passes the unmultiplied title count buffer (`crates/victory-gpu/src/draw.rs:1853-1879`)
In `draw.rs`, `indirect::bound` writes `min(counts[0], records) * 17` into `clamped` at `host_stride * host_max`, and the `#[cfg(feature = "diagnostics")]` `read_indirect` block reads that multiplied count — **but the `ExecuteIndirect` call right above it still passes the original title count buffer**:
```rust
list.list.ExecuteIndirect(
    &signature,
    host_max,
    &clamped,
    0,
    counter.as_ref().map(|(s, _)| &s.buffer),
    counter.as_ref().map_or(0, |(s, at)| s.offset(*at)),
)
```
For any counted indirect compute dispatch (e.g. title count = 1, `x = 80,000`), `ExecuteIndirect` reads count `1` instead of `17` and drops chunks `1..16`.
Also, in the `diagnostics` block below it, `if chunked { Some((&clamped, ...)) }` passes `Some` even when `counter` is `None` (where `count_word` was `false` and nothing was allocated/written at that offset). Both `ExecuteIndirect` and `read_indirect` should use `Some((&clamped, u64::from(host_stride) * u64::from(host_max)))` if and only if `chunked && counter.is_some()`.

### 3. 17x buffer under-allocation in `indirect::bound` (`crates/victory-gpu/src/indirect.rs:676-679`)
```rust
let host_stride = if chunked { 16 } else { stride };
let words = (host_stride / 4) as u64 * u64::from(records.max(1));
let count_word = chunked && count.is_some();
let out = list.arguments(4 * (words + u64::from(count_word)))?;
```
`words` multiplies by `records` instead of `records * 17` when `chunked` (`kind == 3`), even though the clamp shader writes `records * 17 * 4` words plus the count word at index `records * 17 * 4`. Small counts (`records <= 240`) happen to be masked by `list.arguments`'s 64 KiB floor, but any `records > 240` overflows the UAV buffer on the GPU.

### 4. Three logic bugs in the `kind == 3` clamp HLSL (`crates/victory-gpu/src/indirect.rs:520-594`)
- **Accepted chunked dispatches never deduct from `left` / `budget[0]`**: in the `lane == 0` loop, `else { left -= costs[i]; }` is attached to `if (kind == 3) { ... } else if (costs[i] > left) { ... } else { left -= costs[i]; }`, so `left -= costs[i]` never executes for `kind == 3`.
- **Multi-record / cross-tile budget rejection leaves chunks unzeroed**: storing a single scalar `reject` means a second over-budget title record in the same 64-lane tile (or across a tile boundary) overwrites `reject`, so `h - h % CHUNKS == reject` only zeroes the latest rejected record's remaining chunks while earlier rejected records' chunks `1..16` still run. Since `left` drops to `0` on the first rejection, checking `h >= reject` (once `reject` is set on the first rejected record) cleanly zeroes every chunk from that point on across all remaining tiles.
- **`GROUPS = 2^20` cap is bypassed for `kind == 3`**: `dispatch_cost` returns `0` when `x > GROUPS / (y * z)`, so e.g. `[65535, 65535, 1]` charges `cost = 0` (passes budget) while `clamped` writes `[0, 65535, 65535, 1]` straight into `dest` (4.3B groups), and `[2_000_000, 1, 1]` writes `17 * 65535 = 1,114,095 > 2^20` groups. Please apply the same `GROUPS` clamp/zeroing to `dest` for `kind == 3` as `kind == 2` does.

### 5. `draw::tests::group_base_covers_a_dispatch_past_the_host_limit` silently skips on FXC syntax error (`crates/victory-gpu/src/draw.rs:4017-4198`)
Compiling `SOURCE` directly with Windows SDK `fxc.exe /T cs_5_1 /E main` fails with:
```text
error X3000: syntax error: unexpected token 'out'
```
`out` is a reserved HLSL keyword (`RWStructuredBuffer<uint> out : register(u0);`). Because the test does `let Ok((root, pso)) = compute(...) else { return; // no shader compiler here };`, it silently returns `ok` on every run without dispatching anything!
Once `out` is renamed, there is also a second bug on line 4146: `params[0]` is a Root UAV (`D3D12_ROOT_PARAMETER_TYPE_UAV`), yet `l.SetComputeRootUnorderedAccessView(uav_param, gpu)` passes `slots.0.GetGPUDescriptorHandleForHeapStart().ptr` (a descriptor-heap GPU handle) instead of `out.GetGPUVirtualAddress()` (and `slots` creates an unused raw UAV for an `RWStructuredBuffer<uint>`). Please fix both and assert on compilation failure rather than returning early when `D3DCompile` rejects the shader.

### 6. Architecture / coordination note with `#3086`
Since `#3086` already covers direct dispatches cleanly by placing `GROUP_BASE` inside `stage.user_data` (which is always a `D3D12_ROOT_PARAMETER_TYPE_32BIT_CONSTANTS` root parameter in `pipeline/host.rs:479-492`), note that `D3D12_INDIRECT_ARGUMENT_TYPE_CONSTANT` can target `(param, DestOffsetIn32BitValues = u.index, Num32BitValuesToSet = 1)` directly without needing a separate `GROUP_BASE_SPACE = 3` root parameter or `HostShader`/`shader_cache` schema changes. Also, on the direct-dispatch path, splitting `x > 65_535` even when `group_base` is `None` (as `#3086` does) avoids passing an illegal `x > 65_535` to `ID3D12GraphicsCommandList::Dispatch`.
