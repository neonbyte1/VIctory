## Description

## Problem

Issue #400 measures the guard lock of `crates/victory-gpu/src/watch.rs` held about 600 ms a world frame on an RTX 2080, with write faults taking about 450 µs each, mostly waiting for it. When a write faults on a page a tracker is armed for, the handler saves the page's 64 KiB before opening it, and it did that (a 64 KiB allocation and a `ReadProcessMemory`) **while holding the guard lock**, so every other title thread's fault, every take and every kernel write (`writing`) queued behind the copy.

## Change

The fault reads the bytes it will save with the lock released, then takes the lock again and keeps them only if the page stayed guarded meanwhile. A guarded page's bytes can only change once it is opened, and `open` is the only place that removes a page from the guard set, so a count per page (folded onto 4,096 counters) is bumped there under the lock and compared when the lock is taken again. If it moved, or the page is no longer guarded, the bytes are read under the lock exactly as before. The bytes read ahead go only to the faulting page's own save, never to an alias's. No protection call moves out of the lock (an earlier attempt that made pages read-only outside it was slower: the protection calls cost more while writers keep running).

Review (reading only)
- Lock ordering: `would_save` keeps `c.0` locked while it takes `c.1`, because the shadowed guard is not dropped until the end of the function. It is called with the guard lock held, so its order is guards -> `c.0` -> `c.1`. `take_split` and `Tracked::taken` use the same order (guards -> `c.0` -> `Changed::taken`'s `c.1`). The other paths (`save`, `arm`, `unarm`, `disarm`, `saved`, `refreshed`) take only `c.1`, and none takes the guard lock or `c.0` while holding it. I found no inversion.
- Counter invariant: `open()` (watch.rs:480) is the only place that removes from `protected`, and it is the only `PAGE_READWRITE` call. `Tracked::drop`, `writing` and its drop, `title_memory_remapped`, `title_memory_aliased` and the handler all reach it through `open`. Every way a page stops being guarded therefore bumps `OPENED`. Both the bump and the loads happen under the guard lock, so `Relaxed` is enough. When the page is guarded at both ends and the count is unchanged, the read lies inside one continuously read-only interval. Any holder that has the page un-changed at re-lock took it inside that interval, so giving the read-ahead to the first saving holder (which may not be the one `would_save` matched) is still correct.
- Interleavings checked: a take by another holder during the unlocked read (no open, so the bytes stay valid); `refreshed` running between the read and the insert (it finds no saved entry, as on main, and its bytes equal memory); the tracker being dropped meanwhile (`changed()` reads `holders` again, and an unused read is freed); the page opened and guarded again (the count moves, so it falls back to the read under the lock).
- Assumption carried over from main: a write that bypasses both the handler and `writing` (for example through an alias mapping that is not guarded) is not seen. The read-ahead window does not make this worse, because main read at fault time with the same exposure.

Static review of `9e0eaa81` (`crates/victory-gpu/src/watch.rs`).

The lock-splitting design looks sound:
- Capturing `opened = OPENED.load(Acquire)` before dropping `GUARDS` and rechecking `g.protected.contains(&page)` + `OPENED` after reading the page (while keeping the page read-only during `read_into`) prevents ABA across reopens, aliases, and remaps — `open()` bumps `OPENED` under `GUARDS` before `VirtualProtect` restores write access, so any concurrent unprotect/write forces a retry or sees the page already open.
- Only `holders` with an armed tracker trigger a save, and `saved` is populated after re-acquiring `GUARDS` only if the page stayed protected.

Two minor non-blocking notes:
- In `Changed::would_save`, `let saved = ...` shadows the earlier `MutexGuard` rather than explicitly dropping `self.0` before locking `self.1` (the lock order `changed.0 -> changed.1` is still consistent with the rest of `watch.rs`, so no deadlock, just slightly subtle).
- In `Changed::save`, `read.take_if(...)` moves the snapshot buffer into the first armed tracker; when multiple armed trackers share the same page, subsequent trackers clone as intended.
